1. INTRO — Operating System Fundamentals

🎯 Most important to understand An OS is software in kernel mode that turns ugly hardware into clean abstractions (the extended machine) and shares those resources among programs (the resource manager). Every OS service is reached from user mode through a system call — a controlled TRAP into the kernel.

What is an Operating System?

An OS sits between the hardware (ugly, complicated) and application programs (which want something simple).

The OS is the only software in kernel mode; apps reach it only through system calls.
⭐ Key — the two complementary jobs
  1. Extended (virtual) machine — hides messy hardware behind abstractions: files (not disk blocks), processes (not CPU time-slots), address spaces (not raw RAM).
  2. Resource manager — controls who gets CPU, memory, devices: grants requests, accounts usage, mediates conflicts (multiplexing in time, e.g. CPU, and in space, e.g. memory/disk).
💡 In plain terms Think of a car: the extended machine is the dashboard, wheel and pedals — simple controls that hide the engine. The resource manager is a traffic cop making many cars share one road without crashing.

Two interfaces, two modes

  • Northbound → up toward users/apps (system calls, libraries). Southbound → down toward hardware (drivers).
  • User mode (restricted) vs Kernel mode (full privileges). The CPU enforces it; crossing user→kernel happens via a trap/system call.
💡 In plain terms Kernel mode = the admin/root account that can do anything; user mode = a guest account. The CPU is the bouncer enforcing the line. A crash in the guest account kills one app; a crash in admin can take down the machine.

Computer-hardware review (know the building blocks)

  • CPU — repeats fetch → decode → execute. Special registers: PC (next instruction address), SP (top of stack), PSW (status flags + current mode/privilege bit). Privilege enforced in HW: Intel protection rings (Ring 0 = kernel … Ring 3 = user); ARM privileged vs unprivileged. Modern CPUs: multiple cores, caches L1/L2/L3.
  • I/O — devices attach via a bus to I/O controllers reached through ports; the software driving a controller is a device driver (built-in or loadable module). Buses: PCI, PCIe, DMI, SATA, USB.
⚠️ Don't mix up PC and SP PC (Program Counter) = the address of the next instruction to run — where the program is. SP (Stack Pointer) = the top of the stack — where the most recent data (locals, return addresses) sits. It's the PC, never the SP, that "points to the next instruction." PSW (Program Status Word — not "PWD") holds the condition flags plus the mode bit that says user vs kernel.

💡 In plain terms Register = in your hand; cache = on your desk; RAM = the bookshelf; disk = a warehouse across town. Disk is ~a million times slower than RAM — which is why so much of OS design is about avoiding disk.

OS (= kernel) vs distribution

The Linux kernel (kernel.org) is the OS itself; a distribution (Ubuntu, RedHat, openSUSE) = a specific kernel build + usability/admin software.

💡 In plain terms The kernel is the engine; a distribution is the whole car built around it. Ubuntu and Debian are different car models with the same kind of engine.

Core concepts (a preview of the whole course)

  • Program = static file of instructions on disk. Process = a running instance in memory, picked by the scheduler, run by the CPU.
  • Context switch = save one process's state, load another's. Multitasking: real (multiple cores) vs virtual (time-sharing one core).
  • System call = controlled kernel entry (e.g. read(fd, buf, n)); trace with strace. IPC = processes talking directly. Signals = alerts (kill -9 PID); dispositions: Term, Ign, Core, Stop, Cont.
💡 Signal name vs disposition — the usual confusion A signal is the alert itself (SIGTERM, SIGKILL, SIGSTOP…); its disposition is what happens by default — exactly one of Term (end), Ign (ignore), Core (end + dump core), Stop (pause), Cont (resume). ⚠️ "Stop" means pause/suspend (SIGSTOP / Ctrl-Z) — not end; ending is Term (SIGTERM, the polite "please quit"). And kill is just the command that sends a signal — it is not a disposition.

How a system call actually works (the TRAP)

A system call is not an ordinary function call — it switches the CPU from user to kernel mode. You call a same-named library wrapper (e.g. read); it puts the syscall number in a register and runs TRAP, which jumps to a fixed kernel entry. The kernel dispatches to the handler, runs it, returns. On error: returns −1 and sets errno.

sequenceDiagram

  participant U as User program

  participant K as Kernel entry
  participant H as Syscall handler
  U->>L: read(fd, buf, n) — push args (steps 1–4)
  L->>L: put syscall number in register (5)
  L->>K: TRAP — switch to kernel mode (6)
  K->>H: dispatch by number (7)
  H-->>K: do the work, finish (8–9)
  K-->>L: return to wrapper (10)
  L-->>U: return value, or -1 + errno (11)
Tanenbaum's 11-step count = read(fd, buffer, nbytes).
💡 In plain terms You (user mode) can't walk into the kitchen (kernel). You press a "call staff" button — the TRAP — and the staff does the work and brings the result back.

Why these concepts exist (history in one breath)

(1) Vacuum tubes — no OS, one job at a time. (2) Transistors — batch systems. (3) ICs — multiprogramming (several jobs in memory so the CPU works while one waits on I/O), spooling, timesharing. (4) PCs — GUIs, networking. Multiprogramming is the reason scheduling, memory protection and processes exist.

Self-test click to reveal answers

1. State the two roles/views of an OS, one sentence each.
Answer
Extended/virtual machine: hides ugly hardware behind clean abstractions (files, processes, address spaces) so programs see one simple, uniform interface. Resource manager: allocates and mediates CPU, memory and devices among competing processes — granting requests, accounting for usage, and multiplexing in time (CPU) and space (memory/disk).
📖 Explained above: What is an Operating System? ↗
2. User mode vs kernel mode — and who enforces the split?
Answer
User mode is restricted — no privileged instructions, no direct hardware access — so a crash usually kills only that program. Kernel mode has full privileges, so a fault there can crash the whole machine. The CPU enforces it (Intel protection rings 0–3 / ARM privileged-vs-unprivileged); the only way across is a trap/system call.
📖 Explained above: Two interfaces, two modes ↗
3. Name the three special CPU registers and what each holds.
Answer
PC (Program Counter) = address of the next instruction to execute; SP (Stack Pointer) = top of the current stack; PSW (Program Status Word) = condition/status flags plus the current privilege/mode bit (user vs kernel — this is how the CPU knows which mode it's in).
📖 Explained above: Computer-hardware review ↗
4. The basic CPU instruction cycle?
Answer
Fetch the next instruction from memory (at the address in the PC) → decode it (work out the operation + operands) → execute it → advance the PC and repeat. ⚠️ Instructions come from memory, not the stack (the stack is only scratch space for data/return addresses).
📖 Explained above: Computer-hardware review ↗
5. Order by speed (fastest first) with rough times: main memory, register, magnetic disk, cache.
Answer
Register (~1 ns) → Cache (~2 ns) → Main memory/RAM (~10 ns) → Magnetic disk (~10 ms). Each level is faster but smaller and costlier. The takeaway: disk is ≈ a million times slower than RAM — which is why so much of OS design is about avoiding disk.
📖 Explained above: Memory hierarchy ↗
6. Program vs process.
Answer
A program is a static file of instructions on disk (the compiled binary); a process is a running instance of it loaded into memory with its own state (registers, PC, memory, open files), scheduled and executed by the CPU. One program → many processes.
📖 Explained above: Core OS concepts ↗
7. What is a context switch, and real vs virtual multitasking?
Answer
A context switch saves the current process's CPU state (registers, PC, SP…) into its PCB and restores another process's, so the CPU switches between them — on a scheduling decision, an interrupt, or a blocking call. Real multitasking = truly parallel on multiple cores; virtual = one core time-shared, only appearing simultaneous.
📖 Explained above: Core OS concepts ↗
8. What is a system call? Example + tracing tool.
Answer
The controlled entry point where a user-mode program requests an OS service: it executes a TRAP that switches the CPU to kernel mode, the kernel runs the service, then returns. Examples: read(fd,buf,n), open, write. Trace the calls a program makes with strace.
📖 Explained above: Core OS concepts ↗ · How a system call works (TRAP) ↗
9. OS/kernel vs Linux distribution.
Answer
The OS/kernel (e.g. the Linux kernel from kernel.org) is the core software that manages the hardware; a distribution bundles a specific kernel build + user/admin software (shell, tools, GUI, package manager) — Ubuntu, Debian, RedHat… Analogy: the kernel is the engine, the distribution is the whole car.
📖 Explained above: OS (= kernel) vs distribution ↗
10. Monolithic vs microkernel/modular — and where does Linux fit?
Answer
Monolithic: the whole OS is one program in kernel space — fast (direct calls) but poorly isolated (a driver bug crashes the kernel). Microkernel: minimal kernel (IRQ/scheduling/IPC) + drivers/servers in user space — robust (restart a crashed server) but more IPC overhead. Linux is essentially monolithic but modular: at compile time you choose what's built in vs loaded later as a loadable kernel module (modprobe/lsmod).
📖 Explained above: OS structure ↗
11. Three default signal dispositions.
Answer
Any three of: Term (terminate), Ign (ignore), Core (terminate + dump core), Stop (suspend), Cont (resume). A signal is an OS-delivered alert (e.g. kill -9 PID); each has a default disposition.
📖 Explained above: Core OS concepts ↗
12. Northbound vs southbound interfaces.
Answer
Northbound faces up toward users/applications (the system-call / library interface); southbound faces down toward the hardware (device drivers).
📖 Explained above: Two interfaces, two modes ↗
13. Why is a system call not an ordinary procedure call?
Answer
A normal procedure call never changes privilege level, but a system call must switch the CPU from user to kernel mode. The TRAP instruction does it: as a side effect it enters kernel mode and jumps to a fixed kernel entry (not an arbitrary address), where the kernel dispatches to the matching system-call handler.
📖 Explained above: How a system call works (TRAP) ↗
14. Type 1 vs Type 2 hypervisor.
Answer
Type 1 (bare-metal): the hypervisor runs directly on the hardware with guest OSes on top (ESXi, Xen) — best performance. Type 2 (hosted): runs as an ordinary app on a host OS and uses the host's processes/file system (VirtualBox, VMware Workstation) — easier to install, slower.
📖 Explained above: OS structure (virtual machines) ↗
15. Distinguish layered, microkernel, client-server, exokernel.
Answer
Layered: a stack of layers, each built only on the one below (e.g. THE). Microkernel: a minimal kernel (IRQ/scheduling/IPC) with drivers & servers in user space → robust. Client-server: a microkernel variant — clients send messages to server processes and the kernel just delivers them (works over a network). Exokernel: the kernel only partitions/protects raw resources and a user-level library OS builds the abstractions — the opposite of cloning the machine like a VM.
📖 Explained above: OS structure ↗

2. LINUX — Linux Basics & Shell

🎯 Most important to understand The shell is just an ordinary user program: it reads a command line, takes the first word as a program name, and runs it by forking a child that execs the program while the shell waits. Redirection (< > 2>) and pipes (|) work because every process starts with three open streams — stdin (fd 0), stdout (fd 1), stderr (fd 2) — that the shell can rewire before the program runs.

Hands-on unit: Ubuntu Linux via a terminal, plus the OpenStack cloud lab ("NED"). The exam expects you to recognise commands and know what they do.

UNIX/Linux background & philosophy

  • History: UNIX written at Bell Labs by Ken Thompson (1969, PDP-7), joined by Dennis Ritchie, who invented C so UNIX could be rewritten portably (1973). POSIX standardised the syscall/utility interface. Linux = a UNIX-like kernel by Linus Torvalds (1991) + GNU tools → distributions.
  • ⭐ UNIX philosophy: a small set of basic mechanisms · each tool does one thing well · everything is a file (devices, pipes, sockets via the same read/write) · combine small filters with pipes.

How the shell runs a command (fork / exec / wait)

The shell reads a line; the first word = program name (later words = arguments; -x = flags). It fork()s a copy of itself; the child exec()s the program (replacing itself with that binary from disk); the parent shell wait()s until it finishes. cmd & → the shell does not wait → the job runs in the background. Globs (*, ?) are expanded by the shell before the program runs.

sequenceDiagram
  participant S as Shell (parent)
  participant C as Child process
  participant P as ls program
  S->>C: fork() — clone the shell
  C->>P: exec(/bin/ls) — become the program
  S->>S: wait() — block until child exits
  P-->>S: ls runs, then exits (status)
  S->>S: read next command / print prompt
Run a command = fork a child, the child becomes the program, the parent waits. With & the parent skips the wait.
💡 In plain terms The shell clones itself (fork), the clone turns into the program you asked for (exec), and the original waits for it to finish before giving you the prompt back. & = "don't wait — I'll keep typing."

3. BOOT — Booting a Computer & systemd

🎯 Most important to understand Booting is a chain that bootstraps ever-more-capable software: firmware (in ROM) loads a tiny bootloader from a fixed place → the bootloader loads the kernel → the kernel starts the first user process (systemd, PID 1), which brings up everything else. Each stage knows just enough to find and start the next.
flowchart TB
  F["1 · Firmware (BIOS/UEFI)
in ROM"] --> B["2 · Bootloader (GRUB)"]
  B --> K["3 · Kernel"]
  K --> S["4 · systemd (PID 1)
targets / runlevels"]
  S --> U["5 · User prompt (shell / GUI)"]
Memorise this order. BIOS reads the first sector → finds the active partition → loads a secondary bootloader → loads & starts the OS.

Step 1 — BIOS (Basic Input/Output System)

  • First code at power-on, stored in ROM on the motherboard; HW-specific low-level I/O routines.
  • Runs POST (self-test) → device discovery (scans PCI buses) + init → picks a boot device from the list in CMOS → reads the first sector (the MBR) into RAM and executes it.
⚠️ Don't confuse these three ROM = holds the BIOS program. CMOS = battery-backed memory holding BIOS settings (clock, boot order). MBR (Master Boot Record — a record, not a "register") = first sector of the boot disk (boot code + partition table). The MBR comes from the disk, not from CMOS.

Step 2 — Bootloader (GRUB)

The MBR code loads GRUB. GRUB needs filesystem drivers to read the kernel from the boot partition, loads the kernel into memory, sets registers (PC, PSW) and jumps to its first instruction.

Step 3 — Kernel start-up

  • 3.1 Arch-specific assembly: set up the OS memory map, identify the CPU, compute RAM, disable interrupts, enable the MMU, init caches.
  • 3.2 C main(): init management structures (process table, interrupt/syscall tables, virtual memory, page cache), load drivers, init OS services (syscalls, IPC, signals).

RAMDISK (initrd / initramfs) — the chicken-and-egg problem

The kernel needs drivers (disk, filesystem) to read the disk — but those modules live on that very disk. Solution: an initial RAM disk (initrd/initramfs) stored next to the kernel with the needed modules; the bootloader unpacks kernel + initrd into RAM; the kernel mounts the initrd as a temporary root, uses it to mount the real root FS, then continues.

💡 In plain terms You need the key (driver) to open the box (disk), but the key is inside the box. The initrd is a spare key taped to the outside — just enough to open the box and grab the real keys.

systemd (modern init, PID 1)

💡 In plain terms systemd is the system's manager; a .service file is a recipe card telling it what to run and when. You write the card, tell the manager to re-read its binder (daemon-reload), then run it now (start) or pin it to every boot (enable).

  • Targets replace runlevels; on boot systemd activates default.target, pulling in services. A target is a synchronisation point.
  • Unit-file sections: [Unit] (description + dependencies), [Service] (Type=, ExecStart=, Restart=), [Install] (WantedBy= — the hook that makes enable work).

⭐ Key — two independent questions "Should X start?" → Requires= (hard) / Wants= (soft) — they pull a unit in. "In what order?" → After= / Before= — ordering only, start nothing. To get "X first, then me" you need both Requires=X and After=X (Requires= alone starts X in parallel).

4. PROC-I — Process Fundamentals

🎯 Most important to understand A process = a program in execution with its own address space and state, tracked by the OS in a PCB. New processes are made by fork (copy, via copy-on-write) usually followed by exec (replace image). Running many at once (multiprogramming) keeps the CPU busy while others wait on I/O.

Why run many processes? Modeling multiprogramming

⭐ Key — the exam formula If a process waits on I/O a fraction p of the time, and n processes are in memory, the chance all are waiting is pⁿ, so CPU utilization = 1 − pⁿ (n = degree of multiprogramming). Example: p = 0.8 → 1 process = 20% CPU; ~10 processes needed to push idle below 10%.
💡 In plain terms One waiter (CPU) serving many tables (processes): while one table reads the menu (I/O wait), the waiter serves another. More tables = the waiter is idle less often.
💡 Where 1 − pⁿ comes from Each process is waiting on I/O a fraction p of the time. If the n processes wait independently, the chance that all n wait at the same moment is p × p × … = pⁿ — and that's the only time the CPU has nothing to do. So CPU busy = 1 − pⁿ. It pays off with diminishing returns: at p = 0.5 you get 50% → 75% → 94% for n = 1, 2, 4 — each extra process only closes part of the remaining idle gap.

Program vs process

A program is a static compiled binary on disk; a process is a running instance in memory with its own state (registers, PC, memory, open files), an owner (effective UID), and an environment. One program → many processes. Tools: ps aux/ps -ef, top, env, jobs/bg/fg (after Ctrl-Z).

💡 Initialized vs uninitialized globals — and what BSS is An initialized global (int n = 5;) has a value to store, so it's written into the binary and loaded into the Data segment. An uninitialized global (int n;) has no value to store, so the binary only records "reserve this many bytes" — that region is the BSS (Block Started by Symbol), which exec zero-fills at load. So "uninitialized" does not mean "unused/not yet called" — it means it starts at 0 and costs no space in the file (only in RAM at run time).

fork / exec / wait — the Unix model

  • fork() duplicates the parent → a child in a separate address space. Returns 0 in the child, the child's PID in the parent (−1 on error).
  • exec (execve) replaces the image with a new program (fresh code/stack/heap/data).
  • wait/waitpid — the parent blocks until the child exits and reaps its exit status (zombie control).
⭐ Copying the address space — two strategies Distinct address space: copy all read-write pages at fork — simple but wasteful. Copy-on-Write (COW): parent & child share pages (read-only) until one writes, then only the touched page is copied. Linux uses COW (a fork is usually followed by exec, so eager copying would be wasted).
💡 In plain terms fork = photocopy yourself; COW = don't actually copy a page until someone scribbles on it. exec = the copy then becomes a different program.

Hierarchy, zombies & termination

  • PID 1 (init/systemd) is the ancestor of all user processes (pstree). A zombie = a terminated process whose exit status the parent hasn't reaped (its slot lingers). An orphan (parent died) is re-parented to PID 1, which reaps it.
  • Four ways to terminate: (1) normal/voluntary (exit), (2) voluntary on error, (3) involuntary error (segfault, div-by-zero → OS kills), (4) killed by request (kill -9).
💡 In plain terms A zombie is a process that has died but whose "death certificate" (exit status) nobody has collected yet — the parent collecting it via wait clears the slot.
⚠️ Orphan vs zombie — the classic mix-up They are opposite orderings. Child dies first, parent hasn't reaped → ZOMBIE (dead, but its exit-status slot lingers until the parent waits). Parent dies first, child still running → ORPHAN (very much alive — it's just adopted by PID 1, which reaps it when it eventually exits). So a process that outlives its parent is an orphan, not a zombie.
⚠️ PID 1 and PID 2 are not "the kernel" The kernel is not a process and has no PID — it runs in the kernel-mode half of every process. PID 1 = systemd (the first user-space process and the ancestor of all the others); PID 2 = kthreadd (the parent of all kernel threads, shown as [kthreadd]). Both are owned by root.

💡 Reading the four transitions
  • Ready → Running — the scheduler picks it and hands it the CPU (a "dispatch").
  • Running → Ready — its time-slice ran out or a higher-priority task showed up (preempted). It can still run — just not this instant.
  • Running → Blocked — it asked for something it must wait for (disk read, key-press, a lock). Holding the CPU would be pointless, so it sleeps.
  • Blocked → Ready — the thing it waited for arrived (I/O finished, event fired). It's runnable again but must queue for the CPU.
⭐ Note there is no Blocked → Running edge: a just-woken process always re-joins the Ready queue first — it can't jump straight onto the CPU.

Process Control Block (PCB)

The per-process record the OS keeps: process mgmt (registers, PC, PSW, SP, state, priority, PID, parent, signals, CPU time), memory mgmt (segment pointers), file mgmt (cwd, file descriptors, UID/GID). In Linux: a doubly linked list of struct task_struct.

💡 Why the PCB exists When a process is not on the CPU, it lives only as its PCB — that record is the process while it's paused. A context switch is literally: copy the live CPU registers into the old process's PCB, then load the new process's PCB back into the registers. Without the PCB the OS would have nowhere to stash a paused process's state, so it could never pause and later resume anything. Linux strings these records (struct task_struct) into a list the scheduler walks.

Threads

A thread is a sub-entity owned by a process; threads share the process's address space and data and cooperate (processes compete). Threads let a process keep progressing when one part blocks.

Shared (per process)Private (per thread)
address space, globals, open files, child processes, signal handlers, accountingPC, registers, stack, state
⚠️ The thread trap: code is SHARED, and so is the PID Threads of one process share the address space — and that includes the code/instructions, plus the heap, globals and open files. They also share the PID (the process's ID); each thread additionally has its own TID, but they all belong to one process. What's truly private is only what a thread needs to run on its own: its own stack, registers, PC and state. So "private = instructions and PID" is backwards — both of those are shared.
⭐ Why threads (1) Simpler than one big finite-state machine for many blocking activities; (2) 10–100× cheaper than a process (no new address space); (3) real parallelism on multicore + overlap compute with I/O.

💡 M:1 vs 1:1, fork vs clone, kernel vs user thread — in plain terms
  • M:1 (user-space threads): a library juggles many threads inside one process the kernel sees. Switching is fast (no kernel crossing), but because the kernel schedules the whole process, it can't spread the threads across cores (no SMP) and one blocking system call freezes all of them.
  • 1:1 (kernel threads): the kernel knows each thread, so it can run them on different cores and one blocking call only blocks that thread — the price is a kernel crossing to create/switch, so it's a bit heavier. Linux uses 1:1.
  • fork vs clone: same "make a new task" family. fork() shares nothing (child gets its own copy of memory); clone() lets you tick boxes for what to share (address space, file descriptors, signals). A "thread" is just a clone that shares the address space.
  • Kernel thread vs user thread: a user thread runs your app code in user space; a kernel thread ([kworker], [ksoftirqd], [kthreadd]) runs only OS code and never returns to user space — it does background jobs like flushing disk buffers, so it has a PID/state and is scheduled like any task but has no user-mode side.

5. SCHED — Scheduling Processes

🎯 Most important to understand The scheduler picks which ready task runs next to optimise goals that conflict (throughput vs response time vs deadlines). Know the trade-offs: FCFS is simple but suffers the convoy effect; SJF/SRTN minimise average turnaround but need known run-times; RR gives fairness/responsiveness (tuned by the quantum); Linux's default CFS shares the CPU by virtual runtime.

The problem

The scheduler decides which task runs next; the dispatcher moves it onto the CPU (does the context switch). Tasks are CPU-bound (long CPU bursts) or I/O-bound (short bursts, often waiting) — schedulers favour I/O-bound/interactive tasks to keep the system responsive.

6. PROC-II — Linux Resource Management (cgroups v2)

🎯 Most important to understand cgroups group processes into a hierarchy and let the kernel limit, account for, and isolate their resource use (CPU, memory, I/O) with hard enforcement — unlike nice, which is only an advisory relative hint. cgroups are the kernel mechanism that makes containers possible.

Why nice isn't enough

nice is weak: only relative values (no global meaning), not strictly enforced, you can renice only your own processes, and it covers only CPU scheduling. cgroups give hierarchical, strict, multi-resource control.

What cgroups v2 are

A kernel feature to (a) organise processes into a tree and (b) distribute resources along it with strict enforcement. A cgroup = a node (a set of processes with limits); a controller = the kernel part distributing one resource (cpu, memory, io…). Every process belongs to exactly one cgroup; new processes inherit the parent's.

The two key rules

⭐ Key constraints Top-down: a controller is enableable only if the parent has it enabled, and can't be disabled while a child still uses it. No-internal-process: a non-root cgroup may distribute resources to children only if it holds no processes itself → processes live in leaves (so they don't compete with the parent's own processes). The root cgroup is exempt.

7. MEM — Memory Management

🎯 Most important to understand Virtual memory gives each process a private linear address space that the MMU translates to physical frames via a page table (address = page number + offset). Only the pages in use need be resident; when RAM fills, the OS picks a victim page to evict (OPT, LRU, Clock…). Be able to split an address and simulate a reference string by hand.

Allocation & fragmentation

Internal fragmentationExternal fragmentation
Whatwasted space inside an allocation (bigger than needed)free gaps between allocations, too small to reuse

Placement: first fit (first hole that fits — fast), best fit (smallest hole — leaves tiny fragments), next fit (resume from last allocation). Buddy algorithm: halve a power-of-two block until the smallest that fits; on free, two adjacent buddies merge. (A asks 100 KB → gets 128 KB; freeing merges back up.)

Virtual memory & paging

Thanks to locality, the whole process needn't be resident. Paging: the address space is split into fixed-size pages; RAM into equal frames; a page table maps pages→frames. Pages needn't be contiguous; it's transparent to the programmer. Resident set = pages in RAM now; working set = pages actively used (⊆ resident). On-demand paging = load a page only when first accessed.

Address translation

With page size = 2ᵏ, the low k bits are the offset. 4 KB page → offset = 12 bits; a 32-bit address → 2²⁰ ≈ 1,048,576 pages.
💡 In plain terms A virtual address is like "apartment building #5, room 204". The building number (page) is looked up to find the real street address (frame); the room number (offset) stays the same.

MMU & TLB (making it fast)

A software table walk needs two memory reads per access (page table + data). The MMU does translation + protection in hardware; the TLB caches recent translations (~64 entries, content-addressable).

Page-table-entry status bits

Valid · Dirty (written → must be saved on evict) · Used/Referenced (LRU input) · Locked (don't swap) · Protected/read-only · Cached, Shared.

⭐ Key — dirty vs clean on eviction A dirty page's RAM copy differs from disk → it must be written back before reuse. A clean read-only page equals its backing store (binary/file) → just discard it and re-read later.

On a page fault with no free frame, evict a victim (local = own frames; global = any — Linux uses global).

Linux memory specifics

  • Multi-level page tables PGD→PUD→PMD→PTE→offset — sparse, only allocate the directories you use (a flat 64-bit table would be enormous).
  • Huge pages (2 MB/1 GB): one TLB entry covers more memory → less TLB pressure; cost = coarser granularity, more waste. Standard page = 4 KB.
  • Buddy allocator = physical frames in power-of-two blocks. Slab allocator sits on top, subdividing pages into same-size kernel objects (inodes, task_struct).
  • Shared libraries: read-only code pages (-fPIC, linked by ld.so) are memory-mapped and shared across processes → save RAM (safe because read-only).
  • OOM killer: Linux over-commits; when memory runs out it kills the process with the highest oom_score (tunable via oom_score_adj). Reclaim uses a two-list LRU / MGLRU.

I/O property dimensions

  • Blocking vs non-blocking = property of the provider (does the call wait?). Synchronous vs asynchronous = the consumer's choice (does it wait?). Orthogonal.
  • Data source (network — real-time, sequential without buffering) vs data space (RAM/disk — pre-exists, random access).
  • Buffering decouples access from generation, decouples speeds, enables rate control + reordering + verification.

10. FILES-I — File Systems

🎯 Most important to understand A file system maps the user's named-file abstraction onto fixed-size disk blocks. The key design choice is how a file's blocks are tracked: contiguous (fast, fragments), linked/FAT (no fragmentation, slow random access), or indexed/i-node (an i-node lists attributes + block addresses, with indirect blocks for big files — what Linux uses). A directory just maps a name → its i-node.

Why file systems exist

Long-term storage must: (1) store large amounts, (2) survive process termination (persistence), (3) allow concurrent access. The FS organises data as linear sequences of fixed-size blocks.

The file abstraction

  • Types: regular, directory, special (char/block device, link, socket, FIFO).
  • Mode string (ls -al) e.g. -rwxr-x---: 1st char = type (- file, d dir, l link, b/c block/char, p pipe, s socket); then 3×3 rwx for owner/group/other. Link count = number of hard references; data freed when it hits 0.

Directories map a name → its i-node. Flat (single root) vs hierarchical (nested). Paths: / root, ~ home, . cwd, .. parent; absolute (from /) vs relative (from cwd).

VFS & on-disk layout

The VFS (Virtual File System) gives one uniform POSIX interface over many concrete FSes (ext4, FAT, NFS…) — each just supplies the functions VFS expects. Per partition: Boot block · Superblock (FS metadata) · free-space mgmt · i-nodes · root dir · files & directories.

  • ext family: ext2 = block groups (superblock · descriptors · bitmaps · i-nodes · data); ext3 = ext2 + journaling; ext4 = JBD journaling, larger limits.

11. FILES-II — Advanced File Systems

🎯 Most important to understand Modern storage is built from a few reusable ideas: copy-on-write (never overwrite; copy a block only when it changes) powers snapshots, BtrFS and container layers; RAID trades disks for speed (striping) and/or redundancy (mirroring/parity); and abstraction layers (LVM, OverlayFS) decouple the filesystem from physical disks.

tmpfs

A filesystem stored in RAM (used for /tmp, /run): read/write = memcpy (very fast) but volatile (lost on reboot). For non-critical temporary data.

Copy-on-Write & snapshots

COW: don't duplicate while only reading — share blocks; on the first write, copy just the changed block. A snapshot shares all blocks with the live FS via COW, so you can take a consistent backup without blocking writes (later writes copy changed blocks elsewhere; the snapshot keeps the old ones).

💡 In plain terms COW = hand everyone the same document to read; only when someone edits it do you photocopy that one page for them. A snapshot = a frozen "as-of-now" view kept cheap by that sharing.

BtrFS

An open-source copy-on-write filesystem (a forest of B-trees) with snapshots, checksums, compression, built-in volume mgmt/RAID. Subvolume = an independently mountable tree; extent = logical→contiguous-physical mapping; chunk = a large device slice. Updates are written to new locations, flushed as atomic checkpoints with a rising generation number; cloned trees use reference counters (freed at refcount 0).

12. Synchronization & Deadlocks

🎯 Most important to understand When processes share data, race conditions (result depends on timing) appear; the cure is mutual exclusion — only one party in the critical region at a time — via semaphores / mutexes / monitors. But locking risks deadlock: processes each waiting for a resource another holds. Deadlock needs all four Coffman conditions at once, so you fight it by breaking one (or by avoidance — the Banker's algorithm).

Race conditions & critical regions

A race condition = the final result depends on the interleaving of accesses to shared data. Classic: two threads each do count++ — both read the old value, both write old+1 → one increment is lost. The code touching shared data is the critical region; protecting it = mutual exclusion.

⭐ Four properties of a good solution (1) No two in their critical regions at once; (2) no assumptions about CPU speed/count; (3) a process outside its CR must not block others; (4) no starvation.

Achieving mutual exclusion

MechanismHow / problem
Disabling interruptsonly works on one CPU; unsafe for user code → kernel-only, short spans
Lock variable / strict alternationnaïve versions still race or force busy-waiting
Peterson / TSL (test-and-set)correct, but busy-wait (a spin lock) — fine only for very short waits
⚠️ Busy-waiting & priority inversion Spinning wastes CPU. Priority inversion: a high-priority task spins for a lock held by a low-priority task that never gets scheduled to release it → no progress. Cure: block (sleep) instead of spin.

Semaphores, mutexes, monitors

  • Semaphore (Dijkstra): an integer with atomic down/P (decrement; block if it would go below 0) and up/V (increment; wake a waiter). Producer–consumer uses three: mutex=1 (buffer lock), empty=N (free slots), full=0 (filled slots). Producer: down(empty); down(mutex); insert; up(mutex); up(full).
  • Mutex = a binary semaphore for locking only (Linux: futexes — fast user-space path, kernel only when blocking).
  • Monitor = a language construct where the compiler guarantees only one process is active inside at a time (you can't forget to lock). Condition variables (wait/signal) block inside the monitor. Message passing (send/receive) needs no shared memory → works across machines.
💡 Classic problems Producer–consumer (bounded buffer) · dining philosophers (5 forks → deadlock if all grab the left fork) · readers–writers (many readers OR one writer).

Deadlocks

⭐ The four Coffman conditions (ALL must hold) (1) Mutual exclusion; (2) hold-and-wait; (3) no preemption; (4) circular wait. Break any one → no deadlock possible.
flowchart LR
  C(("process C")) -->|wants| T["resource T"]
  T -->|held by| D(("process D"))
  D -->|wants| U["resource U"]
  U -->|held by| C
Resource-allocation graph: circles = processes, squares = resources. A cycle (here C→T→D→U→C) = a deadlock (one unit per resource).

Four strategies:

StrategyWhat
Ostrichignore it (most OSes — deadlocks are rare)
Detection & recoverylet them happen, detect cycles, recover (kill/preempt/roll back)
Avoidancegrant only if the state stays safe → the Banker's algorithm
Preventionstructurally negate one condition (sharing, request-all-up-front, preemption, global ordering)
💡 Safe state & Banker's A safe state = some ordering lets every process get its max and finish. The Banker's algorithm pretends to grant a request and checks the result is still safe. ⭐ An unsafe state is not yet a deadlock, but completion can't be guaranteed. (Starvation ≠ deadlock; livelock = busy but no progress.)

Erklaerung

🎯 Wichtigste IdeePeripherieregister sind memory-mapped: Die CPU greift mit normalen LDR/STR-Befehlen ueber Register-Adresse = Basisadresse + Offset zu, kein Spezialbefehl noetig.
⭐ Key
  • Register-Adresse = Basisadresse (aus Memory Map / Reference Manual) + Offset; z.B. GPIOA 0x4002'0000 + OSPEEDR-Offset 0x08 = 0x4002'0008.
  • Little Endian (Cortex-M4): LSB liegt an der niedrigsten Adresse; 0x8899'AABB @ 0x2100'0248 ergibt 0xBB an ...248, 0x88 an ...24B.
  • Bus-Steuersignale sind alle active-low (N-Praefix): NWE='0' = Write, NOE='0' = Read, NE markiert Beginn/Ende des Buszyklus; Richtung immer an NWE/NOE ablesen.
  • volatile ist Pflicht bei Hardware-Registern, sonst optimiert der Compiler aufeinanderfolgende Zugriffe weg (zwei Schreibzugriffe zu einem).
  • Adressdekodierung: Full Decoding wertet alle Adressleitungen aus (1:1, genau eine Adresse), Partial Decoding nur einen Teil (n nicht dekodiert -> 2^n Aliase).
⚠️ StolpersteinTypische Buszugriff-Aufgabe: zuerst Richtung (NWE/NOE), dann Adresse + Wert ablesen, und beim Eintragen in den Speicher UNBEDINGT Little-Endian-Bytereihenfolge beachten.

Synchroner Bus: Schreibzyklus typ. 4-5 Takte, Lesezyklus 5-6 Takte, Uebernahme an steigender CLK-Flanke.

Was ist ein Mikrocontroller?

Ein Mikrocontroller (MCU) ist eine "Single Chip Solution": CPU + Speicher + Peripherie + Bus auf einem einzigen Chip. Eine CPU allein kann nichts mit der Aussenwelt machen — sie braucht Speicher (Programm und Daten), Peripherie (LEDs, Taster, Sensoren, Displays) und einen System Bus, der alles verbindet. CT2-Fokus: Wie kommuniziert die CPU mit der Peripherie, wie liest/schreibt man Register, wie funktioniert der Bus.

Peripherie und Register

Peripheral (Peripherie): Ein konfigurierbarer Hardware-Block im Mikrocontroller, der eine Aufgabe von der CPU übernimmt und selbstständig erledigt. Beispiele: GPIO (LEDs/Taster), SPI (serielle Kommunikation), UART, Timer, ADC (Spannung messen).

Die CPU steuert die Peripherie über Register — spezielle Speicherzellen in der Peripherie. Es gibt drei Arten: Control Register (CPU → Peripheral, CPU konfiguriert die Peripherie, z.B. "als Ausgang konfigurieren"); Status Register (Peripheral → CPU, CPU liest den Zustand, z.B. EOC-Flag "Wandlung fertig?"); Data Register (bidirektional, Datenaustausch, z.B. ADC-Ergebnis lesen oder SPI-Byte senden).

Memory-Mapped I/O und Registeradresse

Memory-Mapped I/O: Die Register der Peripherie sind in den normalen Adressraum eingeblendet. Für die CPU sieht ein Peripheral-Register genauso aus wie eine Speicherzelle — Zugriff mit LDR/STR (Assembly) bzw. mit Pointern (C). Modul reg_ctboard stellt auf dem CT-Board die memory-mapped Strukturen wie CT_LCD, CT_BUTTON, CT_LED, CT_DIPSW bereit.

Die wichtigste Formel der Vorlesung: Registeradresse = Basisadresse + Offset. Basisadresse: Wo beginnt das Peripheral im Adressraum (Reference Manual, Table 2). Offset: Welches Register innerhalb des Peripherals (Register-Beschreibung). Beispiel: SPI1 hat Basisadresse 0x4001'3000, Control Register CR1 hat Offset 0x00 → SPI1_CR1 liegt an 0x4001'3000 + 0x00 = 0x4001'3000.

System Bus und Bussignale

System Bus: Verbindet die CPU (Master) mit Speicher und Peripherie (Slaves). Drei Gruppen von Leitungen: Adressleitungen, Datenleitungen, Steuersignale.

Bussignale im Detail: A[31:0] (Master → Slave, 32 Adressleitungen, unidirektional, 2^32 = 4 GB Adressraum); D[31:0] (bidirektional, 32 Datenleitungen, wer treibt hängt von Read/Write ab); CLK (Master → Slave, Takt, synchronisiert alle Transfers); NE = Not Enable / Chip Enable (Master → Slave, '0' = Bus-Zyklus aktiv, definiert die Zugriffsdauer); NWE = Not Write Enable (Master → Slave, '0' = Schreibzugriff); NOE = Not Output Enable (Master → Slave, '0' = Lesezugriff); NBL[3:0] = Not Byte Line (Master → Slave, gibt an welche Bytes gültig sind — Word/Half/Byte).

Active-Low und N-Präfix

Namenskonvention N-Präfix: N = NOT = Active-Low. Das Signal ist aktiv wenn '0', inaktiv wenn '1'. NOE='0' → Output IS enabled (Slave treibt Daten) = READ; NOE='1' → nicht enabled. NWE='0' → Write IS enabled (CPU treibt Daten) = WRITE; NWE='1' → nicht enabled. NE='0' → Bus-Zyklus aktiv; NE='1' → kein Bus-Zyklus. Merkregel: NWE aktiv (='0') → geschrieben (Write); NOE aktiv (='0') → gelesen (Read); nie beides gleichzeitig.

Bus-Timing: Write und Read

Bus-Timing Write-Zyklus (4 Takte): CPU schreibt Daten an eine Adresse.

Assembly Write: LDR R0,=0x21000248 / LDR R1,=0x8899AABB / STR R1,[R0].

Bus-Timing Read-Zyklus (5 Takte — einen mehr als Write, da die CPU im Timeslot T5 zusätzlich Zeit braucht, um die Daten einzulesen): CPU liest Daten von einer Adresse.

Assembly Read: LDR R0,=0x2100134C / LDR R1,[R0].

Zugriffsbreite und Little Endian

Bus Access Size: STR R0,[R1] = Word, 4 Bytes (32 Bit), alle NBL[3:0] aktiv; STRH R0,[R1] = Half-word, 2 Bytes (16 Bit), NBL[1:0] aktiv; STRB R0,[R1] = Byte, 1 Byte (8 Bit), NBL[0] aktiv.

Little Endian: ARM Cortex-M ist Little Endian — das niederwertigste Byte (LSB) liegt an der niedrigsten Adresse. Kochrezept: 32-Bit Wert W in 4 Bytes aufteilen (je 2 Hex-Ziffern, von rechts), Bytes aufsteigend den Adressen zuweisen. Beispiel W = 0xBBCCDDEE @ Adresse A: A+0 = 0xEE (LSB), A+1 = 0xDD, A+2 = 0xCC, A+3 = 0xBB (MSB).

Tri-State und Bus Contention

Tri-State — Problem Bus Contention: Am Datenbus hängen mehrere Geräte (CPU, Speicher, Peripherie). Treiben zwei Geräte gleichzeitig — eines '1' (VCC), das andere '0' (GND) — entsteht ein Kurzschluss. Lösung Tri-State Buffer: Hat drei Zustände statt zwei. ENABLE='1' → Ausgang = Eingangswert (aktiv, treibt den Bus); ENABLE='0' → Ausgang = 'Z' (High Impedance / hochohmig / floating, elektrisch abgekoppelt, als wäre der Draht abgetrennt). So kann ein anderes Gerät den Bus treiben. Wenn kein Gerät treibt, "schwebt" die Leitung — der Wert ist unbestimmt (in Timing-Diagrammen schraffiert dargestellt).

💡 Tri-State-BufferENABLE=1: Ausgang = Eingangswert (treibt den Bus). ENABLE=0: Ausgang = Z (hochohmig/floating, abgekoppelt) — verhindert Bus Contention.

Address Decoding

Address Decoding: Am Bus hängen viele Slaves. Greift die CPU z.B. auf 0x40020000 zu, darf nur GPIO Port A reagieren — alle anderen müssen ihren Tri-State-Ausgang auf 'Z' lassen. Die Address Decoding Logik in jedem Slave bestimmt "Bin ich gemeint?".

Full Address Decoding: Alle Adressbits werden dekodiert → jede Adresse gehört genau einem Register (1:1). Beispiel: 6 Adressleitungen A[5:0], Adresse 0x28 = 101000b → select = A[5] & !A[4] & A[3] & !A[2] & !A[1] & !A[0] → select='1' nur für 0x28.

Partial Address Decoding: Nur ein Teil der Adressleitungen wird dekodiert. Die nicht dekodierten Bits sind "egal" → das Register ist unter mehreren Adressen erreichbar (Aliasing). Beispiel: 6 Leitungen, nur obere 4 dekodiert: select = A[5] & A[4] & !A[3] & !A[2] → Muster 1100XXb → erreichbar unter 0x30, 0x31, 0x32, 0x33. Allgemein: n nicht dekodierte Bits → 2^n Aliase.

⚠️ StolpersteinPartial Decoding: jedes nicht dekodierte Bit verdoppelt die Anzahl Aliase (n Bits → 2^n Adressen fuer dasselbe Register).

Kochrezept Adressdekodierung — Gleichung → Adressen: 1. Feste Bits bestimmen (A[n] ⇒ Bit=1, !A[n] ⇒ Bit=0). 2. Fehlende Bits = X (egal). 3. Alle Kombinationen für X aufschreiben. 4. Binär → Hex umrechnen. Adresse → Gleichung: 1. Adresse in Binär. 2. Für jedes Bit A[n] (wenn 1) oder !A[n] (wenn 0). 3. Mit & verknüpfen (Full); für Partial nur die gewünschten Bits aufnehmen.

C-Zugriffe und Bitoperationen

C-Registerzugriffe — volatile-Pointer Syntax: #define REGISTER (*((volatile typgroesse *)(ADRESSE))). Aufbau von innen nach aussen: (ADRESSE) = Hex-Adresse des Registers; (volatile typgroesse *) = Cast zu volatile-Pointer; * davor = Dereferenzieren (Wert lesen/schreiben, nicht Adresse). volatile sagt dem Compiler: Dieses Register kann sich jederzeit von aussen (Hardware) ändern, Zugriffe NICHT wegoptimieren, nicht cachen, nicht zusammenfassen. Typgröße: uint8_t (8-Bit, 1 Byte), uint16_t (16-Bit, Half-Word), uint32_t (32-Bit, Word). Der Cast-Typ bestimmt auch die Buszugriffsbreite. CT-Board-Beispiel: #define CT_LED (*((volatile uint16_t *) 0x60000100)), #define CT_DIPSW (*((volatile uint16_t *) 0x60000200)).

Übersicht Bitoperationen: Bit n setzen REG |= (1 << n); (OR mit Maske, Rest bleibt); Bit n löschen REG &= ~(1 << n); (AND mit invertierter Maske, Rest bleibt); Bit n testen if (REG & (1 << n)) (Ergebnis != 0 wenn gesetzt); Bit n pollen while (!(REG & (1 << n))){} (wartet bis gesetzt); alle Bits setzen REG = 0xFFFFFFFF;; Wert schreiben REG = wert; (überschreibt alles). Warum |= statt =? Mit = werden alle anderen Bits überschrieben; mit |= (Read-Modify-Write) bleibt der Rest erhalten. Trick: (1 << n) ist die Maske für Bit n, z.B. Bit 15 = (1 << 15) = 0x8000.

Hex-Masken Referenz: Bit 0 = 0x0000'0001, Bit 1 = 0x0000'0002, Bit 2 = 0x0000'0004, Bit 3 = 0x0000'0008, Bit 4 = 0x0000'0010, Bit 7 = 0x0000'0080, Bit 8 = 0x0000'0100, Bit 15 = 0x0000'8000, Bit 16 = 0x0001'0000, Bit 24 = 0x0100'0000, Bit 25 = 0x0200'0000, Bit 30 = 0x4000'0000, Bit 31 = 0x8000'0000.

Externer Bus (FMC, CT-Board)

Externer synchroner Speicherbus (Bus Cycles, CT-Board): Der STM32F429ZI besitzt einen 16-Bit breiten externen Datenbus, angesteuert über den FMC (Flexible Memory Controller). Der Bus ist synchron — alle Transfers sind an CLK gebunden. Auf dem externen Bus heissen die relevanten Bussignale: CLK (Takt); NE (Chip Enable, active-low, definiert Zugriffsdauer, Pin PD7 analog); NOE (Output Enable / Read, active-low); NWE (Write Enable / Schreiben, active-low); NBL0 (Lower Byte Lane Enable, active-low); NBL1 (Upper Byte Lane Enable, active-low); A[10:8] (Adressbits); D[15:0] (16-Bit Datenbus).

CT-Board Architektur (Datenpfad CPU → Peripherie):

Die CPU greift über den internen System Bus auf den FMC zu; der FMC übersetzt interne Zugriffe in externe Buszyklen; das CPLD (Complex Programmable Logic Device) dekodiert die Adresse und steuert die richtige Peripherie an. Das CT-Board muss in Modus 3 betrieben werden, damit der externe Bus auf den Steckern P1–P4 verfügbar ist.

Zugriffsbreite durch Datentyp (16-Bit-Bus): uint8_t * = 8 Bit (Byte), 1 Buszyklus, eine Byte Lane aktiv; uint16_t * = 16 Bit (Halfword), 1 Buszyklus, beide Byte Lanes aktiv; uint32_t * = 32 Bit (Word), 2 Buszyklen, weil der externe Bus nur 16 Bit breit ist.

Byte Lane Signale (NBL0 = Lower / unteres Byte, NBL1 = Upper / oberes Byte) zeigen an, welche Hälfte des 16-Bit Datenbusses gültige Daten enthält: Halfword (16-Bit) → NBL0=0 aktiv, NBL1=0 aktiv, gültig D[15:0] (alle); Byte Even (gerade Adresse) → NBL0=0 aktiv, NBL1=1 inaktiv, gültig D[7:0] (unteres Byte); Byte Odd (ungerade Adresse) → NBL0=1 inaktiv, NBL1=0 aktiv, gültig D[15:8] (oberes Byte). Wichtig: Beim Read Cycle erfolgt keine Byte-Signalisierung über NBL — das CPLD liefert immer alle 16 (bzw. 32) Bit, und die CPU ignoriert intern die nicht benötigten Bytes. Die Byte Lane Signale sind nur beim Write Cycle relevant.

Read Cycle vs. Write Cycle (extern): Read Cycle (Lesen von Peripherie) — NE geht low → NOE geht low → Peripherie legt Daten auf den Bus → CPU liest bei steigender Flanke; dauert länger, weil die CPU im Timeslot T5 zusätzlich Zeit zum Einlesen braucht; CPLD liefert immer 32-Bit Daten unabhängig von Halfword/Word. Write Cycle (Schreiben an Peripherie) — NE geht low → NWE geht low → CPU legt Daten auf den Bus → Peripherie übernimmt bei steigender Flanke; kürzer als Read, da die CPU keine Daten einlesen muss.

Aligned vs. Unaligned

Aligned vs. Unaligned Zugriffe: Ein aligned Zugriff bedeutet, dass die Adresse ein Vielfaches der Zugriffsbreite ist — Byte: jede Adresse ist aligned; Halfword: Adresse muss gerade sein (Adresse mod 2 = 0); Word: Adresse muss durch 4 teilbar sein (Adresse mod 4 = 0). Ein Halfword-Zugriff auf eine ungerade Adresse (unaligned) erfordert zwei separate Buszyklen, weil die gewünschten 16 Bit auf zwei verschiedenen Byte-Positionen liegen, die nicht in einem einzigen 16-Bit Buszyklus übertragen werden können. Konsequenz: Daten immer aligned im Speicher ablegen.

CT-Board Register/Adressen (externer Bus): CT_LED LEDs 7…0 @ 0x60000100 (D[7:0] oder D[15:0], 8/16/32-Bit Zugriff); CT_LED LEDs 15…8 @ 0x60000101 (D[15:8], 8-Bit odd); CT_DIPSW S7…0 @ 0x60000200 (D[7:0] oder D[15:0]); CT_DIPSW S15…8 @ 0x60000201 (D[15:8], 8-Bit odd). NBL0/NBL1 liegen am Control Bus (P4), NE an Pin PD7.

Gemessene Bus-Zugriffszeiten (CT-Board, Logic Analyzer): t_read = 644 ns; t_write = 644 ns; t_read→write = 440 ns; t_write→read = 784 ns.

2. GPIO hoch

Erklaerung

🎯 Wichtigste IdeeJeder Pin wird ueber mehrere Register konfiguriert (MODER/OTYPER/OSPEEDR/PUPDR), und Ausgaben setzt man atomar ueber BSRR statt ueber ODR.
⭐ Key
  • Bit-Position fuer 2-Bit-Register (MODER, OSPEEDR, PUPDR): Bits [2n+1:2n] (Offset = 2*n); OTYPER/IDR/ODR nur 1 Bit [n]. Beispiel Pin 13: MODER[27:26].
  • MODER-Codes auswendig: 00 Input, 01 General Purpose Output, 10 Alternate Function, 11 Analog (fuer ADC).
  • BSRR ist 32 Bit: Bits [15:0] setzen einen Pin (ODR:=1), Bits [31:16] loeschen ihn (ODR:=0); '0' schreiben = keine Aenderung. Set: BSRR = (1<<n), Reset: BSRR = (1<<(16+n)).
  • Push-Pull (OTYPER=0, treibt aktiv '0' und '1') vs. Open-Drain (OTYPER=1, treibt nur '0', braucht externen Pull-Up fuer '1', noetig fuer I2C / Wired-OR).
⚠️ Stolperstein
  • BSRR statt direktem ODR, weil ODR-Maskierung ein Read-Modify-Write ist: ein Interrupt zwischen Lesen und Zurueckschreiben kann eine Aenderung verlieren. BSRR ist EIN atomarer Schreibzugriff.
  • Open-Drain ohne externen Pull-Up liefert keinen definierten High-Pegel - der Pin floatet hochohmig.
💡 In einfachen WortenHAL/Struct statt nackter Pointer: Register als volatile-Struct reg_gpio_t ueber #define GPIOG ((reg_gpio_t*)0x4002'1800) ansprechen; Feldreihenfolge muss exakt den Offsets entsprechen. Alternate Function via AFRL (Pin 0-7, 0x20) / AFRH (Pin 8-15, 0x24), 4 Bit/Pin.

Was ist GPIO und Pin Sharing

GPIO (General Purpose Input/Output) sind die einfachsten I/O-Pins eines Mikrocontrollers: Ein Pin wird als Eingang (Taster lesen) oder Ausgang (LED steuern) konfiguriert. Der STM32F429 hat 144 Pins, aber mehr Funktionen (GPIO, SPI, UART, Timer, ADC...) als Pins — deshalb teilen sich mehrere Funktionen einen Pin (Pin Sharing); ueber Konfigurationsregister waehlt man, welche Funktion ein Pin gerade hat.

Ports und Register

Die Pins sind in Ports organisiert (Port A bis K, 11 Ports), jeder Port hat bis zu 16 Pins (z.B. A.0 bis A.15) und denselben Satz von 10 Registern — nur die Basisadresse aendert sich.

Basisadressen der Ports

Basisadressen liegen ab 0x4002'0000, jeweils 0x400 (1024 Bytes) auseinander: GPIOA=0x4002'0000, GPIOB=0x4002'0400, GPIOC=0x4002'0800, GPIOD=0x4002'0C00, GPIOE=0x4002'1000, GPIOF=0x4002'1400, GPIOG=0x4002'1800, GPIOH=0x4002'1C00, GPIOI=0x4002'2000, GPIOJ=0x4002'2400, GPIOK=0x4002'2800. Trick: Basisadresse(Port) = 0x40020000 + Index * 0x0400 (Port G = Index 6 = 0x40020000 + 6 * 0x0400 = 0x40021800).

💡 In einfachen WortenPort-Index = A=0, B=1, ... G=6: einfach Index mal 0x400 auf die Basis 0x40020000 addieren.

Jeder physische Pin hat eine Nummer (1-144) und einen GPIO-Namen (aus dem Datasheet, Seite 19 Pinout / Seite 46 Pin-Tabelle): z.B. Port A.3 = Pin 37, Port E.1 = Pin 142.

Registeradresse = Port-Basisadresse + Register-Offset. Uebersicht der 10 Register (Offset | Bits/Pin | Zugriff | Funktion): MODER 0x00 | 2 | r/w | Modus Input/Output/AF/Analog; OTYPER 0x04 | 1 | r/w | Ausgangstyp Push-Pull/Open-Drain; OSPEEDR 0x08 | 2 | r/w | Ausgangsgeschwindigkeit; PUPDR 0x0C | 2 | r/w | Pull-up/Pull-down; IDR 0x10 | 1 | r | Eingangsdaten lesen; ODR 0x14 | 1 | r/w | Ausgangsdaten schreiben; BSRR 0x18 | — | w | Einzelne Bits atomar setzen/loeschen; LCKR 0x1C | 1 | r/w | Konfiguration sperren; AFRL 0x20 | 4 | r/w | Alternate Function Pin 0-7; AFRH 0x24 | 4 | r/w | Alternate Function Pin 8-15.

Die 4 Konfigurationsregister

Die 4 Konfigurationsregister im Detail.

1. MODER (Offset 0x00, 2 Bit/Pin): bestimmt die Grundfunktion. 00 = Input (Taster lesen); 01 = General Purpose Output (LED ansteuern); 10 = Alternate Function (Pin von anderem Peripheral gesteuert: SPI, UART, Timer); 11 = Analog (ADC-Eingang, Schmitt-Trigger abgeschaltet). Bits fuer Pin n: [2n+1 : 2n], also Pin 0 = [1:0], Pin 3 = [7:6], Pin 13 = [27:26], Pin 15 = [31:30].

2. OTYPER (Offset 0x04, 1 Bit/Pin): bestimmt den elektrischen Ausgangstyp, nur relevant wenn MODER = 01 oder 10. 0 = Push-Pull (kann aktiv HIGH und LOW treiben, Standard fuer LEDs); 1 = Open-Drain (kann nur aktiv LOW treiben, braucht externen Pull-up fuer HIGH). Bit fuer Pin n: einfach Bit [n] (Pin 3 = Bit 3). Haeufiger Fehler: OTYPER hat als einziges Konfigurationsregister nur 1 Bit/Pin, nicht 2.

⚠️ StolpersteinOTYPER und IDR/ODR sind 1-Bit-Register (Bit [n]); MODER/OSPEEDR/PUPDR sind 2-Bit ([2n+1:2n]).

3. OSPEEDR (Offset 0x08, 2 Bit/Pin): Flankensteilheit des Ausgangssignals; hoehere Speed = steilere Flanken, aber mehr Stromverbrauch und EMC-Probleme. 00 = Low, 01 = Medium, 10 = High, 11 = Very High. Bits fuer Pin n: [2n+1 : 2n]. Faustregel: fuer LEDs/Taster reicht Low oder Medium.

4. PUPDR (Offset 0x0C, 2 Bit/Pin): aktiviert interne Widerstaende. 00 = kein Pull (Pin schwebt/floating wenn nichts angeschlossen); 01 = Pull-up (Ruhezustand HIGH); 10 = Pull-down (Ruhezustand LOW); 11 = Reserved (nicht verwenden). Bits fuer Pin n: [2n+1 : 2n]. Noetig wenn der Pin als Eingang konfiguriert ist und kein externer Widerstand vorhanden ist — sonst ist ein offener Eingang undefiniert (floating). Floating-Pins sind extrem stoerungsanfaellig (Fingerprobe: der Koerper koppelt als Antenne 50-Hz-Netzstoerungen ein).

Datenregister: IDR, ODR, BSRR

Die Datenregister.

IDR (Offset 0x10, 1 Bit/Pin, read-only): Bit n = aktueller logischer Zustand von Pin n (0 oder 1). Liest immer den Pin-Zustand, auch wenn der Pin als Ausgang konfiguriert ist (nuetzlich bei Open-Drain um zu pruefen, ob ein anderes Geraet den Bus auf LOW zieht).

ODR (Offset 0x14, 1 Bit/Pin, r/w): ODR Bit n = 1 → Pin n HIGH; = 0 → Pin n LOW. Aenderung einzelner Bits erfordert Read-Modify-Write (ODR = ODR | (1<<13)), was nicht atomar und durch Interrupts unterbrechbar ist.

BSRR (Offset 0x18, write-only): bevorzugtes Register zum atomaren Setzen/Loeschen einzelner Pins. Bits [15:0] = BS (Set): '1' schreiben setzt Pin auf HIGH; Bits [31:16] = BR (Reset): '1' schreiben setzt Pin auf LOW; '0' = keine Aenderung. Ein einziger Schreibzugriff, andere Bits bleiben unveraendert, nicht unterbrechbar. Pin n HIGH: BSRR = (1 << n); Pin n LOW: BSRR = (1 << (16+n)). Beispiele: Pin 13 HIGH = 0x0000'2000; Pin 13 LOW = 0x2000'0000; Pin 13 HIGH + Pin 14 LOW = (1<<13) | (1<<(16+14)) = 0x4000'2000.

Push-Pull vs. Open-Drain

Push-Pull vs. Open-Drain. Push-Pull hat zwei Transistoren (P-MOS oben, N-MOS unten): bei ODR='1' leitet der P-MOS → Ausgang VDD (HIGH), bei ODR='0' leitet der N-MOS → Ausgang GND (LOW). Beide Richtungen werden aktiv getrieben; gut fuer LEDs und schnelle Signale; funktioniert unabhaengig von der Eingangs-Konfiguration zuverlaessig. Open-Drain hat nur den unteren N-MOS plus externen Pull-up-Widerstand: bei ODR='0' zieht der N-MOS den Pin auf GND, bei ODR='1' sperrt der N-MOS und der Pin schwebt (wird vom externen Pull-up auf VDD gezogen). Vorteil: Mehrere Geraete koennen am gleichen Draht haengen, ohne Kurzschluss — jeder kann auf LOW ziehen, ohne Zieher ist der Draht HIGH (Wired-AND / Wired-OR, Level-Shifting). Wird bei I2C verwendet. Ohne Pull-up liefert ein Open-Drain-Ausgang bei "1" einen undefinierten, floatenden Pegel.

Clock Enable und Debugger-Pins

GPIO Clock Enable. Bevor auf GPIO-Register zugegriffen werden kann, muss der Peripheral Clock des Ports aktiviert werden: GPIOA_ENABLE(); bzw. GPIOB_ENABLE(); (setzt das jeweilige Bit in RCC->AHB1ENR). Ohne Clock Enable bleiben alle Schreibzugriffe auf GPIO-Register wirkungslos.

Debugger-Pins schuetzen. Bei GPIOA und GPIOB sind nur die Pins 11-0 fuer den Anwender frei; Pins 15-12 sind fuer den Debugger reserviert (JTAG/SWD). Werden sie umkonfiguriert, kann der Debugger nicht mehr zugreifen und das Board ist nicht mehr programmierbar. Schutz: reset_GPIO() (Register auf Reset-Werte), request_abort_startup() (stoppt bei gedruecktem Taster T0-T3 vor der Konfiguration), config_check_GPIOA() (prueft MODER auf erwarteten Wert).

HAL: Register-Struct statt roher Pointer

HAL (Hardware Abstraction Layer). Statt jedes Register mit roher Adresse anzusprechen, verwendet man ein Struct (definiert in reg_stm32f4xx.h): typedef struct { volatile uint32_t MODER; OTYPER; OSPEEDR; PUPDR; IDR; ODR; BSRR; LCKR; AFRL; AFRH; } reg_gpio_t; — die Felder liegen in derselben Reihenfolge und mit denselben Offsets wie die Hardware-Register. Die Basisadressen sind Makros, die die Adresse zu einem Pointer auf diesen Struct casten: #define GPIOA ((reg_gpio_t *) 0x40020000), #define GPIOB ((reg_gpio_t *) 0x40020400), #define GPIOG ((reg_gpio_t *) 0x40021800). Zugriff: GPIOA->MODER = 0x55555555; (alle 16 Pins Output), GPIOG->BSRR = (1<<13);, uint32_t btn = GPIOA->IDR & 0x1;. Da die Felder volatile sind, optimiert der Compiler die Zugriffe nicht weg — der Hardware-Zugriff findet garantiert statt. GPIOA->OTYPER greift automatisch auf 0x40020000 + 0x04 = 0x40020004 zu.

Clear-then-Set und Kochrezept

Clear-then-Set Pattern. Beim Konfigurieren immer erst die betroffenen Bits mit invertierter Maske loeschen, dann den Wert setzen — nie direkt zuweisen, sonst werden andere Bits ueberschrieben: register &= ~(bit_maske << bit_position); (Clear), dann register |= (neuer_wert << bit_position); (Set).

Kochrezept: GPIO-Pin konfigurieren. 1) Welcher Port und Pin? (aus Aufgabe/Datasheet, z.B. Pin 37 → Port A, Bit 3; Basisadresse nachschlagen). 2) Welche Register? Ausgabe → MODER + OTYPER + OSPEEDR + PUPDR (alle 4); Eingabe → MODER + PUPDR (OTYPER/OSPEEDR irrelevant). 3) Welche Adressen? Registeradresse = Basisadresse + Offset. 4) Welche Bits? Pin n: MODER/OSPEEDR/PUPDR an [2n+1:2n], OTYPER an [n]. 5) Welche Werte? aus der Aufgabenstellung. 6) C-Code: Bit setzen |=, Bit loeschen &= ~, ganz schreiben =.

Kritisch: Open-Drain ohne Pull-up (PB1) mit No Pull Input (PA2) — bei Ausgang "1" sind beide Seiten floating, der Wert ist undefiniert und stoerungsanfaellig. Auch PB1 mit Pull-down-Input ist problematisch, weil der Pull-down den gewuenschten High-Pegel verhindert. In der Praxis braucht ein Open-Drain-Ausgang immer einen Pull-up (am Ausgang oder Eingang).

3. SPI hoch

Erklaerung

🎯 Wichtigste IdeeSPI ist synchron (gemeinsamer SCLK), full-duplex und Master/Slave: Master und Slave bilden ein ringfoermiges Schieberegister, nach 8 Takten ist ein Byte komplett in beide Richtungen ausgetauscht.
⭐ Key
  • 4 Signale: SCLK (Master->Slave), MOSI (Master Out Slave In), MISO (Master In Slave Out), SS (active-low; pro Slave eine eigene Leitung, SCLK+MOSI parallel).
  • Die 4 Modi: Mode 0 (CPOL=0,CPHA=0, idle LOW, Sample steigende Flanke), Mode 1 (0/1, idle LOW, fallende), Mode 2 (1/0, idle HIGH, fallende), Mode 3 (1/1, idle HIGH, steigende). CPOL = Idle-Pegel, CPHA=0 -> 1. Flanke, CPHA=1 -> 2. Flanke.
  • STM32-Register: SPI_CR1 (SPE, MSTR, BR[2:0], CPOL/CPHA, LSBFIRST, DFF=8/16-Bit), SPI_SR (TXE, RXNE, BSY), SPI_DR (Write=TX, Read=RX). Baudrate: f_SPI = f_PCLK / 2^(BR+1).
  • Software-Ablauf Polling: SPE=1, erstes TX-Byte in DR (loescht TXE), Loop: warte TXE=1 -> write DR -> warte RXNE=1 -> read DR; am Ende warte TXE=1 UND BSY=0.
⚠️ StolpersteinSPI hat KEINE Fehlererkennung, kein Acknowledge, kein Flow-Control und kein Adressschema (Auswahl nur ueber SS-Pins); MSB/LSB-first ist nicht standardisiert.
💡 In einfachen WortenSS='1' schaltet MISO des deselektierten Slaves auf Tri-State (hochohmig) - so teilen sich mehrere Slaves dieselbe MISO-Leitung.

Was ist SPI?

SPI (Serial Peripheral Interface) ist ein serielles, synchrones, full-duplex Protokoll, um einen Mikrocontroller mit externen Geraeten zu verbinden (Displays, Flash-Speicher, Sensoren, ADCs). De-facto-Standard von Motorola (~1979), ohne offizielle Spezifikation.

Seriell statt parallel: wenige Leitungen (4 statt 32+), kleiner Platzbedarf auf dem PCB, wenige Pins, bessere EMC; dafuer muessen Bits nacheinander gesendet werden. SPI ist der Kompromiss: wenige Leitungen, aber trotzdem schnell (bis ~50 MHz Clock).

Die 4 Leitungen

Die 4 SPI-Leitungen sind SCLK, MOSI, MISO und SS.

SCLK (Serial Clock): Takt, Richtung Master → Slave, wird vom Master generiert; alle Teilnehmer arbeiten im Gleichschritt.

MOSI (Master Out, Slave In): Daten fliessen vom Master zum Slave (Master sendet, Slave empfaengt).

MISO (Master In, Slave Out): Daten fliessen vom Slave zum Master (Slave sendet, Master empfaengt).

SS (Slave Select, auch NSS): Master → Slave, active-low; der Master zieht SS auf LOW, um den Slave zu aktivieren. Jeder Slave hat eine eigene SS-Leitung (kein Adressierungsschema).

Wichtige Eigenschaften: Synchron (Master erzeugt SCLK), Full-Duplex (MOSI + MISO gleichzeitig), Master-Slave (nur der Master kontrolliert die Kommunikation), Auswahl ueber individuelle SS-Leitungen.

Mehrere Slaves und Tri-State auf MISO

Mehrere Slaves: SCLK und MOSI gehen parallel an alle Slaves. MISO liegt bei allen am gleichen Draht, deshalb Tri-State: SS='1' → Slave-MISO = 'Z' (hochohmig, gibt den Bus frei), SS='0' → Slave-MISO aktiv (treibt Daten). Jeder Slave braucht eine eigene SS-Leitung (SS1, SS2, SS3, ...).

Shift-Register-Prinzip

Shift-Register-Prinzip: Master und Slave haben je ein 8-Bit Shift-Register, ueber MOSI und MISO zu einem Ring verbunden. Bei jedem SCLK-Takt wird 1 Bit in jede Richtung geschoben: Master schiebt ein Bit ueber MOSI in das Slave-Register, der Slave schiebt ein Bit ueber MISO in das Master-Register. Nach 8 Takten haben Master und Slave ihre Daten komplett ausgetauscht.

Folge des Shift-Prinzips: Senden und Empfangen geschehen immer gleichzeitig. Wer nur senden will, ignoriert das empfangene Byte; wer nur empfangen will, sendet ein Dummy-Byte (z.B. 0x00).

💡 In einfachen WortenSenden und Empfangen sind untrennbar gekoppelt: nur empfangen = Dummy-Byte senden, nur senden = RX-Byte verwerfen.

Status-Flags TXE/RXNE/BSY

Status-Flags der Hardware: TXE (TX Buffer Empty) → TX-Buffer leer, CPU darf naechstes Byte schreiben; RXNE (RX Buffer Not Empty) → ein Byte empfangen, CPU darf es lesen; BSY (Busy) → Uebertragung laeuft noch.

CPOL und CPHA: die 4 Modi

CPOL/CPHA-Modi (sehr pruefungsrelevant): Da SPI keine offizielle Spezifikation hat, muessen Master und Slave denselben Modus verwenden. CPOL (Clock Polarity) bestimmt den Ruhezustand (Idle-Level) des Takts; CPHA (Clock Phase) bestimmt, an welcher Taktflanke die Daten gesampelt (uebernommen) werden.

CPOL=0 → SCLK idle = LOW; CPOL=1 → SCLK idle = HIGH.

CPHA=0 → Sampling an der ERSTEN Flanke nach SS aktiv; CPHA=1 → Sampling an der ZWEITEN Flanke nach SS aktiv.

Mode 0: CPOL=0, CPHA=0 → idle LOW, Toggling = fallende Flanke, Sampling = steigende Flanke.

Mode 1: CPOL=0, CPHA=1 → idle LOW, Toggling = steigende Flanke, Sampling = fallende Flanke.

Mode 2: CPOL=1, CPHA=0 → idle HIGH, Toggling = steigende Flanke, Sampling = fallende Flanke.

Mode 3: CPOL=1, CPHA=1 → idle HIGH, Toggling = fallende Flanke, Sampling = steigende Flanke.

Toggling Edge = hier stellt der Sender das naechste Datenbit auf die Leitung (Daten wechseln); Sampling Edge = hier liest der Empfaenger das Bit (Daten abtasten). Es sind immer entgegengesetzte Flanken: erst bereitstellen (Toggle), dann uebernehmen (Sample).

⭐ KeyMerksatz: erst Toggle (Bit bereitstellen), dann Sample (Bit lesen) - immer auf entgegengesetzten Flanken.

Bit Cell (Dauer einer Bitzelle) = 1 / f_SCLK. Beispiel: 100 kHz → 1/100000 = 10 us = 0.01 ms.

STM32-Register und Bitbelegung

STM32F4xxx-Register: SPI_CR1 (Offset 0x00, r/w) = Control Register 1, gesamte Konfiguration. SPI_CR2 (Offset 0x04, r/w) = Control Register 2, Interrupts und DMA. SPI_SR (Offset 0x08, r) = Status Register. SPI_DR (Offset 0x0C, r/w) = Data Register; TX und RX teilen sich dieses Register (Schreiben → TX-Buffer, Lesen → RX-Buffer).

SPI-Basisadressen: SPI1 = 0x4001'3000 (APB2), SPI2 = 0x4000'3800 (APB1), SPI3 = 0x4000'3C00 (APB1), SPI4 = 0x4001'3400 (APB2), SPI5 = 0x4001'5000 (APB2), SPI6 = 0x4001'5400 (APB2).

SPI_CR1 Bit 0: CPHA — Clock Phase (0 = 1. Flanke sampeln, 1 = 2. Flanke sampeln).

SPI_CR1 Bit 1: CPOL — Clock Polarity (0 = idle LOW, 1 = idle HIGH).

SPI_CR1 Bit 2: MSTR — Master Selection (0 = Slave, 1 = Master).

SPI_CR1 Bits [5:3]: BR[2:0] — Baud Rate Prescaler, teilt den Bus-Takt (SPI-Takt = f_PCLK / 2^(BR+1)).

SPI_CR1 Bit 6: SPE — SPI Enable (0 = aus, 1 = ein); muss als LETZTES gesetzt werden, danach sind alle Settings scharf.

SPI_CR1 Bit 7: LSBFIRST — Bit Order (0 = MSB first, 1 = LSB first).

SPI_CR1 Bit 8: SSI — Internal Slave Select; bei SSM=1 ersetzt dieser Wert intern den NSS-Pin, SSI=1 haelt NSS intern HIGH und verhindert MODF.

SPI_CR1 Bit 9: SSM — Software Slave Management (0 = Hardware-NSS, 1 = SS per Software/GPIO steuern).

SPI_CR1 Bit 10: RXONLY — Nur-Empfangsmodus (0 = Full-Duplex, 1 = nur Empfang).

SPI_CR1 Bit 11: DFF — Data Frame Format (0 = 8 Bit, 1 = 16 Bit).

SPI_CR1 Bit 12: CRCNEXT — naechster Transfer ist CRC (0 = kein CRC).

SPI_CR1 Bit 13: CRCEN — CRC-Berechnung (0 = deaktiviert, 1 = aktiviert).

SPI_CR1 Bit 14: BIDIOE — Output Enable im bidirektionalen Modus (nur relevant bei BIDIMODE=1).

SPI_CR1 Bit 15: BIDIMODE — bidirektionaler Datenmodus (0 = 2-line unidirectional mit separatem MOSI+MISO, 1 = 1-line bidirectional).

Baudrate und Prescaler

Baud Rate Prescaler bei f_PCLK = 42 MHz: BR=000 → /2 = 21 MHz; 001 → /4 = 10.5 MHz; 010 → /8 = 5.25 MHz; 011 → /16 = 2.625 MHz; 100 → /32 = 1.3125 MHz; 101 → /64 = 656 kHz; 110 → /128 = 328 kHz; 111 → /256 = 164 kHz.

SPI_CR2 Bit 7: TXEIE — TX Buffer Empty Interrupt Enable. Bit 6: RXNEIE — RX Buffer Not Empty Interrupt Enable. Bit 5: ERRIE — Error Interrupt Enable. Bit 2: SSOE — SS Output Enable (fuer Hardware-SS).

SPI_SR Bit 0: RXNE — RX Buffer Not Empty, pruefen bevor man SPI_DR liest. Bit 1: TXE — TX Buffer Empty, pruefen bevor man SPI_DR schreibt. Bit 6: OVR — Overrun Error (RX-Daten nicht rechtzeitig abgeholt). Bit 7: BSY — Busy, Uebertragung laeuft noch. Nach Reset ist TXE=1 (Buffer leer) und RXNE=0 (nichts empfangen).

SPI_DR: Schreiben laedt das Byte in den TX-Buffer und startet die Uebertragung; Lesen liefert das empfangene Byte aus dem RX-Buffer und loescht RXNE.

Software Slave Select im Lab: Statt Hardware-NSS wird SS manuell ueber GPIO PA4 gesteuert. SSM=1 (physischer NSS-Pin wird intern ignoriert), SSI=1 (internes NSS=HIGH, verhindert MODF), PA4 als normaler Output (nicht AF). SS LOW (Slave aktiv): GPIOA->BSRR = 0x00100000 (Bit 4 im Reset-Teil). SS HIGH (Slave inaktiv): GPIOA->BSRR = 0x00000010 (Bit 4 im Set-Teil).

GPIO Alternate Function: Die SPI-Pins SCK/MISO/MOSI werden im AF-Mode (MODER=10) betrieben, dadurch uebernimmt die SPI-Peripherie die Pin-Steuerung. AF5 = SPI1 auf dem STM32F429. Belegung: PA4 = NSS (Output, manuell), PA5 = SCK (AF5), PA6 = MISO (AF5), PA7 = MOSI (AF5), PA8 = SBUF (Input). Clock-Aktivierung noetig: RCC->APB2ENR Bit 12 (SPI1EN), RCC->AHB1ENR Bit 0 (GPIOAEN).

Master-Konfigurationsreihenfolge (RM S.861): 1. BR[2:0] setzen, 2. CPOL und CPHA setzen, 3. DFF setzen, 4. LSBFIRST konfigurieren, 5. SSM und SSI setzen (bei Software-NSS), 6. MSTR setzen, 7. SPE als Letztes setzen.

Software-Ablauf (Polling)

Software-Ablauf Full-Duplex Polling (Einzelbyte, RM S.864-866): 1. SS low setzen (Slave aktivieren). 2. Warten bis TXE=1 (TX-Buffer bereit). 3. Byte in SPI_DR schreiben (startet automatisch die Clock-Erzeugung). 4. Warten bis RXNE=1 (Empfang abgeschlossen). 5. SPI_DR lesen (empfangenes Byte holen, loescht RXNE). 6. Warten bis BSY=0 (Transfer komplett). 7. 10 us warten (SS erst nach letzter Clock-Flanke hochsetzen, sonst geht das letzte Bit verloren). 8. SS high setzen (Slave deaktivieren).

Was intern beim Schreiben in DR passiert: Byte → TX-Buffer → Shift-Register (TXE wird wieder 1) → Bits seriell auf MOSI hinausgeschoben; gleichzeitig werden Bits von MISO ins Shift-Register hineingeschoben; nach 8 Taktzyklen Shift-Register → RX-Buffer (RXNE wird 1).

C-Code Ablauf (mehrere Bytes, reines Senden mit TXE-Polling):

SPI1->CR1 |= (1 << 6);          // SPE = 1, SPI einschalten
SPI1->DR = 0xF1;                // erstes Byte, startet Uebertragung, loescht TXE
while (!(SPI1->SR & (1 << 1))); // warte bis TXE = 1
SPI1->DR = 0xF2;                // naechstes Byte
while (!(SPI1->SR & (1 << 1))); // warte TXE
SPI1->DR = 0xF3;                // letztes Byte
while (!(SPI1->SR & (1 << 1))); // TXE = 1
while (SPI1->SR & (1 << 7));    // BSY = 0, Uebertragung komplett

C-Code Ablauf Lab (hal_spi_read_write, full-duplex Einzelbyte):

set_ss_pin_low();
while (!(SPI1->SR & BIT_TXE)) {}    // warte bis TX-Buffer leer
SPI1->DR = send_byte;               // Byte ins Data Register
while (!(SPI1->SR & BIT_RXNE)) {}   // warte bis RX-Buffer voll
rec_byte = SPI1->DR;                // empfangenes Byte lesen
while (SPI1->SR & BIT_BSY) {}       // warte bis SPI nicht mehr busy
wait_10_us();
set_ss_pin_high();
return rec_byte;

Vor- und Nachteile

Vorteile von SPI: hohe und flexible Datenrate (Clock wird mitgesendet, Master bestimmt das Tempo); echtes Full-Duplex; einfache Hardware (Shift-Register), KISS-Prinzip; keine Adressierung noetig.

Nachteile von SPI: keine Adressierung (stattdessen je Slave eine SS-Leitung, viele Pins bei vielen Slaves); keine Fehlererkennung (muss in hoeherer Schicht implementiert werden); keine Empfangsbestaetigung (Slave kann kein ACK senden); kein Flow-Control (Slave kann den Master nicht bremsen); Bit-Reihenfolge MSB/LSB first nicht standardisiert; stoerempfindlich (Spikes auf SCLK koennen Extra-Bits erzeugen).

4. UART & I2C hoch

Erklaerung

🎯 Wichtigste IdeeUART ist asynchron (Sync nur ueber die fallende Flanke des Start-Bits), I2C ist synchron mit zwei Open-Drain-Leitungen (SDA+SCL) und Acknowledge nach jedem Byte.
⭐ Key
  • UART-Frame: [Idle=1][Start=0][5-8 Datenbits, LSB first][opt. Paritaet][1/1.5/2 Stoppbits=1]; Sender und Empfaenger brauchen identische Einstellungen.
  • Die 3 UART-Formeln: T_bit = 1/Baudrate; Durchsatz = Baudrate / N_Frame mit N_Frame = 1(Start)+N_Daten+N_Paritaet+N_Stopp; delta_max = 0.5 / (N+0.5) * 100% (N = Datenbits).
  • I2C-Phasen: START (SDA faellt bei SCL=HIGH) -> 7-Bit-Adresse + R/W -> ACK -> Datenbytes je ACK/NACK -> STOP (SDA steigt bei SCL=HIGH). SDA-Wechsel nur bei SCL=LOW erlaubt.
  • Vergleich: SPI 4 Leitungen(+SS)/synchron/full-duplex/Auswahl per SS/schnell; UART 2/asynchron/full-duplex/keine Adressierung; I2C 2/synchron/half-duplex/ACK/7-Bit-Adresse.
⚠️ StolpersteinACK ist active-low: '0' = ACK, '1' = NACK. Ein SDA-Wechsel bei SCL=HIGH wird IMMER als START/STOP gedeutet, nie als Datenbit. Bei der Durchsatz-Formel zaehlen Start+Stopp mit, Paritaet nur wenn aktiv.
💡 In einfachen WortenNACK hat fuenf moegliche Ursachen, nicht nur "Fehler": keine passende Adresse, Empfaenger nicht bereit, Kommando nicht verstanden, Empfaenger voll, ODER der Master beendet bewusst eine Lesetransaktion (letztes Byte -> Master sendet NACK + STOP).

UART-Grundlagen

UART = Universal Asynchronous Receiver Transmitter — serielle Schnittstelle ohne gemeinsamen Takt; Sender und Empfaenger muessen die gleiche Baudrate eingestellt haben, Synchronisation erfolgt ueber das Start-Bit.

UART-Leitungen (TX/RX)

Leitungen: TX (Transmit) sendet, RX (Receive) empfaengt; TX von A geht auf RX von B (und umgekehrt) — die Leitungen kreuzen sich.

UART ist Full-Duplex (Senden und Empfangen gleichzeitig ueber 2 getrennte Leitungen) und Punkt-zu-Punkt (nur 2 Geraete, kein Bus).

UART-Frame

UART-Frame Aufbau: Idle (HIGH) | Start (LOW) | D0 D1 ... (Datenbits, LSB zuerst) | [Parity] | Stop (HIGH) | [Stop] | Idle.

Idle: HIGH (1), beliebig lang — kein Datenverkehr, Leitung ruht auf HIGH.

Start-Bit: LOW (0), 1 Bit — signalisiert den Beginn der Daten.

Datenbits: 5-9 Bit, LSB zuerst gesendet — die eigentlichen Nutzdaten.

Parity: 0 oder 1 Bit, optional (Even/Odd) — zur Fehlererkennung.

Stop-Bit(s): HIGH (1), 1-2 Bit — markiert das Ende des Frames.

Drei UART-Frame-Details: LSB first (niederwertigstes Bit zuerst), Idle = HIGH (Leitung ruht auf HIGH), Start-Bit = LOW (Uebergang HIGH→LOW = fallende Flanke zur Synchronisation).

UART-Synchronisation ueber Start-Flanke

Synchronisation: Der Empfaenger erkennt die fallende Flanke des Start-Bits (1→0), weiss dann, dass alle T_bit Sekunden ein neues Bit kommt, und sampelt jedes Bit in der Mitte der Bitperiode mit der vereinbarten Baudrate.

Die 3 UART-Formeln

UART-Formel 1 (Bitperiode): T_bit = 1 / Baudrate.

UART-Formel 2 (Durchsatz): Bytes/s = Baudrate / Bits_pro_Frame, mit Bits_pro_Frame = 1 (Start) + Datenbits + Paritybits + Stoppbits.

UART-Formel 3 (Maximale Taktabweichung): Max_Abweichung = 0.5 / (N + 0.5) * 100%, mit N = Anzahl Datenbits; der Empfaenger synchronisiert an der Start-Flanke und muss bis zum letzten Datenbit (N+0.5 Bitperioden spaeter) noch in der richtigen Mitte sampeln, darf also maximal 0.5 Bitperioden daneben liegen.

I2C-Grundlagen

I2C = Inter-Integrated Circuit — serieller Bus mit nur 2 Leitungen, an dem viele Geraete haengen; jedes Geraet hat eine eigene 7-Bit-Adresse, der Master waehlt per Adresse aus.

I2C-Leitungen und Open-Drain

I2C-Leitungen: SCL (Serial Clock) = Takt, wird vom Master erzeugt; SDA (Serial Data) = Daten, bidirektional (Master und Slave).

Open-Drain: Beide Leitungen sind Open-Drain mit Pull-up-Widerstaenden — jedes Geraet kann die Leitung auf LOW ziehen (N-MOS leitet), keines kann aktiv auf HIGH treiben (Pull-up zieht hoch); Vorteil: kein Kurzschluss moeglich, auch bei mehreren Mastern.

I2C-Eigenschaften: synchron (Master erzeugt SCL), Half-Duplex (SDA abwechselnd von Master/Slave), Multi-Master (Arbitrierung bei Kollision), adressiert (Slave-Auswahl per 7-Bit-Adresse, keine SS-Leitungen); Geschwindigkeiten: Standard 100 kbit/s, Fast 400 kbit/s, High-Speed 3.4 Mbit/s.

I2C START/STOP und Bit-Uebertragung

I2C START-Bedingung: SDA faellt (1→0) waehrend SCL = HIGH.

I2C STOP-Bedingung: SDA steigt (0→1) waehrend SCL = HIGH.

I2C normale Bit-Uebertragung: SDA wechselt nur waehrend SCL = LOW und muss stabil sein waehrend SCL = HIGH (dort wird gesampelt); START und STOP sind die einzigen Situationen, in denen sich SDA bei SCL = HIGH aendert.

⚠️ StolpersteinSDA-Wechsel bei SCL=HIGH wird IMMER als START/STOP gedeutet, nie als Datenbit.

I2C Write-/Read-Frame und ACK/NACK

I2C Write-Frame: START | 7-Bit Slave-Adresse A6..A0 | W(0) | ACK (Slave zieht SDA LOW) | 8-Bit Daten D7..D0 | ACK (Slave bestaetigt) | STOP.

I2C Read-Frame: START | ADDR[6:0] | R(1) | ACK (Slave) | Slave sendet Daten D7..D0 | NACK (Master beendet) | STOP.

ACK: Der Empfaenger zieht SDA im 9. Takt auf LOW — Bedeutung: "Byte empfangen, weiter".

NACK: SDA bleibt im 9. Takt HIGH — Bedeutung: "Fertig" oder "Fehler"; Master sendet NACK nach dem letzten gelesenen Byte, Slave sendet NACK bei nicht erkannter Adresse oder Fehler.

STM32-Register (I2C und USART)

STM32 I2C Basisadressen: I2C1 = 0x4000'5400, I2C2 = 0x4000'5800, I2C3 = 0x4000'5C00 (alle APB1).

I2C_CR1 (Offset 0x00): PE(0) = Enable, START(8), STOP(9), ACK(10).

I2C_CR2 (Offset 0x04): FREQ[5:0] = APB1-Frequenz in MHz.

I2C_DR (Offset 0x10): Datenregister zum Senden/Empfangen.

I2C_SR1 (Offset 0x14): SB(0) = Start gesetzt, ADDR(1) = Adresse bestaetigt, BTF(2) = Byte Transfer Finished, TXE(6) = Sende-DR leer, RXNE(7) = Empfangsdaten da, AF(10) = Acknowledge Failure.

I2C_SR2 (Offset 0x18): BUSY(1) = Bus belegt, MSL(0) = Master/Slave; Lesen von SR2 loescht das ADDR-Flag.

I2C_CCR (Offset 0x1C): CCR[11:0] = Clock Control, F/S(15) = Fast/Standard.

I2C SCL-Frequenz: Standard Mode (100 kHz): CCR = f_PCLK1 / (2 * f_SCL); Fast Mode (400 kHz, DUTY=0): CCR = f_PCLK1 / (3 * f_SCL).

STM32 UART Basisadressen: USART1 = 0x4001'1000 (APB2), USART2 = 0x4000'4400 (APB1), USART3 = 0x4000'4800 (APB1).

USART_SR (Offset 0x00): TXE(7) = DR leer, TC(6) = Transmission Complete, RXNE(5) = Empfangsdaten da, ORE(3) = Overrun Error, PE(0) = Parity Error.

USART_DR (Offset 0x04): Datenregister.

USART_BRR (Offset 0x08): Baudrate (Mantissa + Fraction).

USART_CR1 (Offset 0x0C): UE(13) = Enable, TE(3) = TX Enable, RE(2) = RX Enable, M(12) = Wortlaenge.

USART_CR2 (Offset 0x10): STOP[13:12] (00 = 1 Stop, 10 = 2 Stop).

TXE vs. TC: TXE(7) = "DR ist leer, naechstes Byte kann geschrieben werden" (DR wurde ins Shift Register kopiert); TC(6) = "Uebertragung komplett fertig, auch das Shift Register ist leer und die Leitung ist idle".

💡 In einfachen WortenTXE = DR leer (Shift Register evtl. noch aktiv); TC = alles fertig, Leitung idle.

I2C Master-Write (Polling) Ablauf: BUSY-Flag pruefen (while SR2 & (1<<1)) → START setzen (CR1 |= (1<<8)) und auf SB warten → Adresse senden (DR = (addr<<1)|0) und auf ADDR warten, dann SR2 lesen um ADDR-Flag zu loeschen → Datenbyte senden (DR = data), auf TXE und BTF warten → STOP setzen (CR1 |= (1<<9)).

Vergleich UART/SPI/I2C

Vergleich UART vs. SPI vs. I2C — Leitungen: UART 2 (TX, RX), SPI 4 + SS/Slave, I2C 2 (SCL, SDA).

Vergleich Synchron: UART nein (asynchron), SPI ja, I2C ja.

Vergleich Duplex: UART Full, SPI Full, I2C Half.

Vergleich Adressierung: UART keine, SPI SS-Pins, I2C 7-Bit-Adresse.

Vergleich Multi-Slave: UART nein (1:1), SPI ja (+SS), I2C ja (per Adresse).

Vergleich Multi-Master: UART nein, SPI nein, I2C ja.

Vergleich Speed: UART ~1 Mbps, SPI ~50 MHz, I2C ~3.4 Mbps.

Vergleich Fehlererkennung: UART Parity, SPI keine, I2C ACK/NACK.

Vergleich Output-Typ: UART Push-Pull, SPI Push-Pull, I2C Open-Drain.

Vergleich Anwendung: UART Debug/GPS/PC, SPI Display/Flash/Sensor, I2C EEPROM/Sensor/RTC.

5. Timer & Counter hoch

Erklaerung

🎯 Wichtigste IdeeTimer = Prescaler + Counter (CNT von 0..ARR) + Auto-Reload: aus PSC und ARR die Update-Periode berechnen, dabei IMMER (PSC+1)(ARR+1).
⭐ Key
  • Update-Periode: T_update = (PSC+1)*(ARR+1) / f_timer; nach PSC bzw. ARR aufloesen koennen. Counter-Frequenz: f_CNT = f_timer / (PSC+1).
  • PWM (Up, Mode 1): f_PWM = f_timer / [(PSC+1)(ARR+1)], Duty D = CCR / (ARR+1); CCR aus gewuenschtem Duty berechnen.
  • PWM Mode 1 (HIGH solange CNT < CCR) vs. Mode 2 (invertiert); gleiches Signal mit Down-Counter -> CCR = ARR - high_ticks (z.B. ARR=39999: Mode1/Up CCR=10000=0x2710, Mode2/Down CCR=29999=0x752F).
  • Input Capture: bei Flanke wird CNT in CCR kopiert; Pulsdauer dt = (CCR2 - CCR1) / f_CNT.
⚠️ Stolperstein
  • Off-by-one: immer PSC+1 und ARR+1, weil der Zaehlwert 0 ein gueltiger Schritt ist.
  • UIF-Flag muss in der ISR manuell zurueckgesetzt werden (TIMx->SR &= ~0x01), sonst Endlos-ISR.
💡 In einfachen WortenTimer an APB1 laufen mit verdoppeltem Takt (84 MHz statt 42 MHz APB1) - dieser x2-Multiplier wird gerne uebersehen; bei PSC/ARR gibt es mehrere gueltige Loesungen, solange beide < 65536.

Was ist ein Timer?

Ein Timer ist ein Hardware-Zaehler, der bei jedem (geteilten) Takt um 1 hoch- oder runterzaehlt. Erreicht er seinen Reload-Wert (ARR), springt er auf 0 zurueck (Upcounter) bzw. von 0 auf ARR (Downcounter) und erzeugt ein Update Event (UEV). Daraus laesst sich ein periodischer Interrupt erzeugen, ein PWM-Signal ausgeben oder per Input Capture ein Zaehlerstand einfangen.

Grundstruktur und Zaehlkette

Grundstruktur (Zaehlkette): f_APB1 (84 MHz) → Prescaler (teilt durch PSC+1) → Counter (zaehlt 0..ARR) → Update Event (Interrupt, Reset). Der APB1-Bus laeuft mit 84 MHz; der Prescaler teilt diesen schnellen Takt herunter, der Counter zaehlt mit der reduzierten Frequenz bis ARR.

Die 4 Funktionseinheiten (PSC, CNT, ARR, CCR)

Die 4 Funktionseinheiten: Prescaler (PSC) = Divisor fuer den Eingangstakt, nur jeder (PSC+1)-te Takt wird gezaehlt. Counter (CNT) = aktueller Zaehlwert, +1 (oder -1) pro geteiltem Takt. Reload (ARR) = Maximalwert (Upcounter zaehlt bis ARR dann Ueberlauf auf 0; Downcounter startet bei ARR, zaehlt bis 0). Capture/Compare (CCR) = Vergleichs-/Einfangregister.

Capture vs. Compare

Capture vs. Compare: Capture = "Wert einfangen" — bei externem Event (z.B. steigende Flanke an Pin) wird der aktuelle CNT-Wert in CCR kopiert, der Counter laeuft weiter; gut fuer Frequenz-/Periodenmessung. Compare = "Wert vergleichen" — sobald CNT den CCR-Wert erreicht, wird ein Event/Interrupt ausgeloest, der Counter laeuft weiter; gut fuer PWM und zeitgesteuerte Aktionen.

Die 3 Formeln (f_timer, Overflow, Duty)

Die 3 wichtigsten Formeln — Timer-Frequenz: f_timer = f_APB1 / (PSC + 1). Beispiel: PSC = 8399 → 84'000'000 / 8400 = 10 kHz.

Overflow-Periode: T_overflow = (ARR + 1) * (PSC + 1) / f_APB1 bzw. f_overflow = f_APB1 / ((PSC + 1) * (ARR + 1)). Beispiel: PSC = 8399, ARR = 9999 → T = 10000 / 10000 = 1 Sekunde. Umstellung zum Dimensionieren: (PSC+1) * (ARR+1) = f_APB1 * T_gewuenscht.

PWM Duty Cycle: Duty Cycle = CCR / (ARR + 1) * 100%. Beispiel: ARR = 39999 (40000 Ticks), CCR = 10000 → 25%.

Off-by-one: warum immer +1

Warum immer "+1"? Weil der Zaehler bei 0 anfaengt. PSC = 0 → durch 1 teilen (kein Teilen); PSC = 8399 → durch 8400 teilen. ARR = 9999 → Counter zaehlt 0..9999 = 10000 Schritte. Beide Werte muessen in 16 Bit passen (< 65536).

PWM Mode 1 vs. Mode 2

PWM-Modi — Mode 1 (OC1M = 110): Upcounting HIGH wenn CNT < CCR, LOW wenn CNT >= CCR; Downcounting LOW wenn CNT > CCR, HIGH wenn CNT <= CCR. Je groesser CCR, desto groesser der Duty Cycle (heller die LED). Sonderfaelle: CCR = 0 → 0% (nie HIGH); CCR = ARR+1 → 100% (immer HIGH); CCR = (ARR+1)/2 → 50%.

PWM-Modi — Mode 2 (OC1M = 111, invertiert): Upcounting LOW wenn CNT < CCR, HIGH wenn CNT >= CCR; Downcounting HIGH wenn CNT > CCR, LOW wenn CNT <= CCR. Merkregel: Mode 2 ist das Gegenteil von Mode 1.

Output-Compare-Modi (OCxM)

Weitere Output-Compare-Modi (OCxM[2:0]): 000 = Frozen (Ausgang unbeeinflusst), 001 = Active on match (HIGH bei CNT = CCR), 010 = Inactive on match (LOW bei CNT = CCR), 011 = Toggle (Umschalten bei CNT = CCR), 110 = PWM Mode 1, 111 = PWM Mode 2.

PWM-Kochrezept: 1) ARR → Dezimal: Gesamt-Ticks = ARR+1. 2) CCR → Dezimal: Umschaltpunkt. 3) Mode bestimmen (110 oder 111). 4) Richtung (Up/Down). 5) Logik anwenden: Mode 1 Up → CCR Ticks HIGH; Mode 2 Up → (ARR+1-CCR) Ticks HIGH. 6) Duty Cycle = HIGH-Ticks / (ARR+1). 7) Periode = (ARR+1) / f_timer.

Input Capture

Input Capture: CC1S = 01 in CCMR1 → Capture von TI1. Bei externer Flanke wird CCR1 = aktueller CNT (Snapshot) gesetzt, der Counter laeuft weiter. Periode = CCR(t2) - CCR(t1). Aus der Periode ergibt sich die Frequenz des Eingangssignals.

Register-Referenz und Basisadressen

Timer-Register-Referenz (Offsets): CR1 = 0x00: CEN(0), DIR(4), CMS(6:5), ARPE(7). SMCR = 0x08: SMS[2:0] = Clock Source (000 = intern). DIER = 0x0C: UIE(0) = Update IRQ Enable, CC1IE(1) = Compare IRQ Enable. SR = 0x10: UIF(0) = Update Flag, CC1IF(1) = Compare Flag (in ISR loeschen!). CCMR1 = 0x18: OC1M(6:4) = PWM Mode, CC1S(1:0) = Capture Source; OC2M(14:12) fuer Kanal 2. CCER = 0x20: CC1E(0) = Output Enable, CC1P(1) = Polarity; CC2E(4), CC3E(8), CC4E(12). CNT = 0x24: aktueller Counter-Wert. PSC = 0x28: Prescaler. ARR = 0x2C: Auto-Reload. CCR1 = 0x34: Capture/Compare Channel 1.

CR1-Bits im Detail: Bit 0 CEN = Counter Enable (1 = Timer laeuft, immer zuletzt setzen). Bit 4 DIR = Direction (0 = up, 1 = down). Bits 6:5 CMS = Center-aligned Mode (00 = edge-aligned). Bit 7 ARPE = Auto-Reload Preload Enable.

Basisadressen / IRQs: TIM2 = 0x4000'0000 (APB1, RCC-Bit 0, IRQ 28). TIM3 = 0x4000'0400 (APB1, RCC-Bit 1, IRQ 29). TIM4 = 0x4000'0800 (APB1, RCC-Bit 2, IRQ 30). TIM5 = 0x4000'0C00 (APB1, RCC-Bit 3).

CCMR/CCER bei mehreren Kanaelen: CCMR1 steuert Kanal 1 (OC1M Bits 6:4) und Kanal 2 (OC2M Bits 14:12); CCMR2 steuert Kanal 3 (OC3M Bits 6:4) und Kanal 4 (OC4M Bits 14:12). Beispiel PWM Mode 1 auf drei Kanaelen: CCMR1 = 0x6060 (Kanal 1+2), CCMR2 = 0x0060 (Kanal 3). CCER-Enable-Bits: CC1E(0), CC2E(4), CC3E(8), CC4E(12); z.B. CCER = 0x0111 schaltet Kanal 1, 2 und 3 ein.

Init-Kochrezept und PWM-Ausgabe

Init-Kochrezept (Reihenfolge): 1) Timer-Clock aktivieren: RCC->APB1ENR |= (1 << 1) fuer TIM3. 2) Clock Source intern: TIM3->SMCR &= ~0x07 (SMS = 000). 3) Richtung Upcounter: TIM3->CR1 &= ~(0x7 << 4) (DIR = 0, CMS = 00). 4) Prescaler und Reload: TIM3->PSC = 8399; TIM3->ARR = 1999 (→ 200 ms). 5) Interrupt aktivieren: TIM3->DIER |= (1 << 0) (UIE). 6) NVIC freischalten: NVIC->ISER[0] |= (1 << 29) (TIM3 = IRQ 29). 7) Timer starten: TIM3->CR1 |= (1 << 0) (CEN, immer zuletzt). ISR: void TIM3_IRQHandler(void) { TIM3->SR &= ~0x01; ... } — UIF immer ZUERST loeschen, sonst Endlosschleife. ISR-Name muss exakt mit dem Startup-File uebereinstimmen.

⚠️ StolpersteinCEN immer zuletzt setzen und UIF in der ISR ZUERST loeschen, sonst Endlos-ISR.

PWM-Ausgabe an Pins: Die GPIO-Pins muessen in den Alternate Function Modus (MODER = 10), fuer TIM3 in AF2. Beispiel CT-Board: TIM3_CH1 = PB4 (Rot), TIM3_CH2 = PB5 (Gruen), TIM3_CH3 = PB0 (Blau). Erst CCER-Bit setzen, dann erscheint das Signal am Pin.

Duty-Cycle-Skalierung (z.B. aus 4-Bit-DIP-Switch): Schalterwert 0x0..0xF (0..15) auf CCR abbilden. Schrittweite = (ARR+1) / 15; bei ARR+1 = 60000 → 4000. Formel: CCRx = Schalterwert * 4000. Durch 15 (nicht 16) teilen, damit 0xF exakt 100% ergibt (16 Stufen = 15 Schritte).

6. ADC hoch

Erklaerung

🎯 Wichtigste IdeeEin N-Bit-ADC bildet V_in auf 2^N diskrete Werte ab; die drei Grundformeln (1 LSB, Digitalwert, FSR) sicher anwenden und auf Abrunden achten.
⭐ Key
  • Aufloesung: 1 LSB = V_REF / 2^N; Digitalwert = floor((V_in / V_REF) * 2^N) (abrunden!); FSR = V_REF - 1 LSB.
  • Fehlertypen unterscheiden: Quantisierung (+/-0.5 LSB, unvermeidbar), Offset (konstante Verschiebung, in SW korrigierbar), Gain (falsche Steigung), DNL (Stufenbreite != 1 LSB), INL (Abweichung von Idealgerade), Missing Codes.
  • Flash vs. SAR: Flash = 2^N-1 Komparatoren parallel, 1 Takt, schnell aber teuer (<=8 Bit); SAR = 1 Komparator + DAC, N Takte (Binaersuche), MCU-Standard (8-16 Bit).
  • Konversionszeit STM32F4: T_total = (N_sample + N_conv) / f_ADCCLK, N_conv = 12/10/8/6 Zyklen je Aufloesung, N_sample programmierbar (3..480 via ADC_SMPR); f_S,max = 1/T_total.
⚠️ StolpersteinDigitalwert wird abgerundet (floor), nicht gerundet - z.B. 4.5 V bei 1 LSB = 1 V ergibt 4 (=100b), nicht 5.
💡 In einfachen WortenOffset oft in %FSR: Offset[%FSR] = |Offset_V| / FSR * 100% (z.B. 3-Bit, V_REF=2V, -1.5 LSB -> -0.375 V / 1.75 V = 21.43%); Aufloesung via RES[25:24] in ADC_CR1 (00=12b...11=6b), ADCCLK = APB2CLK / Prescaler.

Was ein ADC macht

Ein ADC (Analog-to-Digital Converter) wandelt eine analoge Eingangsspannung in eine digitale Zahl um. Er misst, wo V_in im Verhaeltnis zur Referenzspannung V_REF liegt, und gibt eine Zahl zwischen 0 und (2^N - 1) aus.

Die drei Grundformeln

Die drei wichtigsten Formeln, auf denen alles aufbaut:

Formel 1 — LSB (Least Significant Bit), die "Schrittweite": 1 LSB = V_REF / 2^N. Der ADC teilt den Bereich (0 bis V_REF) in 2^N gleich grosse Stufen; 1 LSB ist die Breite einer Stufe, also die kleinste unterscheidbare Spannungsaenderung. Beispiel 3-Bit ADC (N=3), V_REF = 2V: 2^3 = 8 Stufen (000 bis 111, also 0 bis 7), 1 LSB = 2V / 8 = 0.25V. Der ADC kann 0V, 0.25V, 0.50V, ... 1.75V unterscheiden.

Formel 2 — Spannung in Digitalwert: Digitalwert = floor(V_in / V_REF * 2^N). floor() bedeutet Abrunden auf die naechste ganze Zahl. Beispiel V_in = 1.1V, V_REF = 2V, N = 3: Digitalwert = floor(1.1 / 2 * 8) = floor(4.4) = 4 = 100 (binaer).

Formel 3 — Digitalwert in Spannung (rueckrechnen): V_approx = Digitalwert * V_REF / 2^N = Digitalwert * 1 LSB. Beispiel Digitalwert = 4, V_REF = 2V, N = 3: V_approx = 4 * 2V / 8 = 4 * 0.25V = 1.0V. Die echte Spannung war 1.1V, der ADC gibt 1.0V zurueck — die Differenz (0.1V) ist der Quantisierungsfehler.

💡 In einfachen WortenQuantisierungsfehler = V_in minus V_approx (hier 0.1 V); maximal +/- 0.5 LSB.

Uebertragungskennlinie und Stufentabelle

Uebertragungskennlinie (Transfer Function): Diagramm, das den Digitalwert fuer jede Eingangsspannung zeigt; sie sieht aus wie eine Treppe. Zeichnen fuer 3-Bit ADC, V_REF = 2V: Achsen zeichnen (X = V_in analog, 0 bis V_REF=2V; Y = Digitalwert, 0 bis 2^N-1 = 7), LSB berechnen (1 LSB = 2V / 8 = 0.25V), Stufen einzeichnen (jede Stufe 1 LSB = 0.25V breit).

Wichtig: Die erste Stufe (000 in 001) springt bei 0.5 LSB ueber Null, also bei 0.5 * 0.25V = 0.125V. Das ist eine Eigenschaft des idealen ADC; die gestrichelte "ideale Linie" verbindet die Mittelpunkte aller Stufen.

Full Scale Range (FSR)

Full Scale Range (FSR): FSR = V_REF - 1 LSB. Der hoechste Wert (z.B. 111 = 7) entspricht V_REF - 1 LSB, nicht V_REF selbst. Beispiel V_REF = 2V, N = 3: FSR = 2V - 0.25V = 1.75V.

Fehlertypen des ADC

Fehlertyp 1 — Quantisierungsfehler (unvermeidbar): Da der ADC kontinuierliche Spannung in diskrete Stufen umwandelt, gibt es immer einen kleinen Fehler, maximal +/- 0.5 LSB. Reduzierbar durch mehr Bits (hoeheres N) oder kleineres V_REF — beides macht 1 LSB kleiner.

Fehlertyp 2 — Offset-Fehler: Die gesamte Treppenkurve ist nach links oder rechts verschoben gegenueber der idealen Kurve; der ADC hat "ab Werk" einen konstanten Fehler. Negativer Offset (z.B. -1.5 LSB): Kurve nach rechts verschoben — der ADC braucht eine hoehere Eingangsspannung fuer denselben Digitalwert, "unterschaetzt" die Spannung systematisch, der erste Treppensprung (000 in 001) passiert spaeter. Positiver Offset (z.B. +1.5 LSB): Kurve nach links verschoben, der ADC "ueberschaetzt" die Spannung.

Fehlertyp 3 — Gain-Fehler: Die Steigung der Treppenkurve stimmt nicht; die Stufen werden immer breiter (positiver Gain-Fehler) oder schmaler. Am Anfang ist der Fehler klein, am Ende gross. Unterschied zu Offset: Offset verschiebt die ganze Kurve gleichmaessig, Gain verzerrt sie (Abweichung waechst mit der Spannung). Zusammenhang: Full-Scale Error = Offset Error + Gain Error.

⭐ KeyOffset verschiebt die ganze Kurve gleichmaessig, Gain verzerrt sie (Fehler waechst mit V_in).

Fehlertyp 4 — DNL (Differentielle Nichtlinearitaet): Die Breite einzelner Stufen weicht von der idealen 1 LSB ab; manche Stufen breiter, manche schmaler.

Fehlertyp 5 — INL (Integrale Nichtlinearitaet): Die gesamte Kurve weicht von der idealen Geraden ab (Summe aller DNL-Fehler).

Fehlertyp 6 — Missing Codes: Wenn DNL so extrem ist, dass eine Stufe komplett verschwindet — ein Digitalwert wird nie ausgegeben.

Architektur: Flash vs. SAR

Architektur Flash ADC (Parallel ADC): Ein Widerstandsnetzwerk (Spannungsteiler) erzeugt 2^N Referenzspannungen; 2^N - 1 Komparatoren vergleichen V_in gleichzeitig mit allen Referenzspannungen; ein Encoder wandelt das Ergebnis in eine N-Bit Zahl. Vorteile: extrem schnell (1 Takt). Nachteile: extrem teuer, braucht viele Komparatoren (3 Bit = 7, 8 Bit = 255, 12 Bit = 4095 Komparatoren). Beispiel: 3-Bit Flash ADC, V_REF = 8V, V_in = 2.3V — Referenzspannungen V_REF/16, 3*V_REF/16, 5*V_REF/16, ... = 0.5V, 1.5V, 2.5V, ...; Komparatoren liefern 0000011 (V_in > 0.5V und > 1.5V, aber < 2.5V); Encoder: 0000011 in 010 (= 2).

Architektur SAR ADC (Successive Approximation Register): Binaere Suche wie beim Erraten einer Zahl — "Ist die Zahl groesser als 8?" bestimmt das MSB, dann das naechste Bit usw. bis alle N Bits feststehen. Aufbau: Komparator + DAC + SAR-Register + Steuerlogik. Braucht N Taktzyklen fuer N Bit Aufloesung. Beispiel 4-Bit SAR, V_REF = 16V, V_in = 11V: Schritt 1 DAC = 8V, V_in(11) > 8V? JA, Bit3 = 1, aktuell 1000 = 8V; Schritt 2 DAC = 12V, V_in > 12V? NEIN, Bit2 = 0, aktuell 1000 = 8V; Schritt 3 DAC = 10V, V_in > 10V? JA, Bit1 = 1, aktuell 1010 = 10V; Schritt 4 DAC = 11V, V_in > 11V? NEIN, Bit0 = 0, aktuell 1010 = 10V; Ergebnis 1010 (= 10), Quantisierungsfehler 11V - 10V = 1V = 1 LSB.

STM32-ADC: Aufbau und Adressberechnung

STM32F429: Hat 3 ADC-Einheiten (ADC1, ADC2, ADC3), jeweils 12-Bit SAR. Jeder ADC kann bis zu 19 Kanaele messen (16 externe Pins + 3 interne: Temperatur, V_REF, V_BAT).

Adressberechnung (gilt fuer alle Peripherals): Jedes Peripheral hat eine Basisadresse, jedes Register einen Offset. Registeradresse = Basisadresse + Offset.

ADC Basisadressen: ADC1 = 0x4001'2000 (ADC-Basis + 0x000), ADC2 = 0x4001'2100 (+0x100), ADC3 = 0x4001'2200 (+0x200), ADC Common = 0x4001'2300 (+0x300).

Beispiel: ADC_SR (Offset 0x00) von ADC2 — ADC2-Basis 0x4001'2100 + 0x00 = 0x4001'2100. Beispiel: ADC3_CR1 (Offset 0x04) — ADC3-Basis 0x4001'2200 + 0x04 = 0x4001'2204.

Die wichtigen ADC-Register

Register ADC_SR — Status Register (Offset 0x00), hier liest die CPU den ADC-Zustand: Bit 5 OVR (Overrun: neues Ergebnis kam, altes nicht gelesen), Bit 4 STRT (Regular channel conversion started), Bit 2 JEOC (Injected end of conversion), Bit 1 EOC (End of Conversion, Wandlung fertig), Bit 0 AWD (Analog watchdog flag). Am wichtigsten: Bit 1 (EOC) und Bit 5 (OVR).

Register ADC_CR1 — Control Register 1 (Offset 0x04): Bits 25:24 RES[1:0] Aufloesung (00 = 12-Bit / 15 ADCCLK-Zyklen, 01 = 10-Bit / 13, 10 = 8-Bit / 11, 11 = 6-Bit / 9), Bit 8 SCAN (Scan Mode, mehrere Kanaele nacheinander), Bit 5 EOCIE (End-of-Conversion Interrupt Enable).

Register ADC_CR2 — Control Register 2 (Offset 0x08): Bit 30 SWSTART (Software Start, loest Wandlung aus), Bit 11 ALIGN (Data Alignment, 0=rechts, 1=links), Bit 1 CONT (Continuous Mode, automatisch wiederholen), Bit 0 ADON (ADC ein/aus).

Register ADC_DR — Data Register (Offset 0x4C): hier steht das Wandlungsergebnis (12-Bit Zahl, 0-4095).

C-Code fuer Register: In CT2 benutzt man volatile-Pointer: #define REGISTER_NAME (*((volatile typgroesse *)(ADRESSE))). volatile sagt dem Compiler "Optimiere diesen Zugriff nicht weg, das Register kann sich jederzeit aendern"; typgroesse ist der Datentyp (uint8_t = 8 Bit, uint16_t = 16 Bit, uint32_t = 32 Bit); ADRESSE ist die berechnete Registeradresse (Basis + Offset).

Wandlungszeit berechnen

ADC-Wandlungszeit: T_total = T_sample + T_conv. T_sample ist die Abtastdauer der Eingangsspannung (konfigurierbar via ADC_SMPR), T_conv die eigentliche Wandlung (haengt von der Aufloesung ab).

T_conv nach Aufloesung in ADCCLK-Zyklen: 12-Bit (00) = 12, 10-Bit (01) = 10, 8-Bit (10) = 8, 6-Bit (11) = 6.

T_sample (konfigurierbar, SMP[2:0] pro Kanal) in Zyklen: 000 = 3, 001 = 15, 010 = 28, 011 = 56, 100 = 84, 101 = 112, 110 = 144, 111 = 480.

ADCCLK berechnen: ADCCLK = APB2CLK / Prescaler. ADC_CCR.ADCPRE[1:0]: 00 = /2, 01 = /4, 10 = /6, 11 = /8.

Rechenbeispiel Wandlungszeit: APB2 = 84 MHz, Prescaler = /4, 12-Bit, SMP = 3 Zyklen: ADCCLK = 84 MHz / 4 = 21 MHz; T_total = (3 + 12) / 21 MHz = 15 / 21'000'000 = 714 ns; Max. Abtastrate = 1 / 714 ns ca. 1.4 MSPS (Mega Samples Per Second).

WELCHE Adresse? Basisadresse_ADCx + Register-Offset. 4. WELCHER Datentyp? uint8_t wenn Bits < 8, sonst uint32_t. 5. WELCHE Maske? 2^Bitnummer in Hex umrechnen. 6. WELCHE Operation? 7. Speicher (Memory) hoch

Erklaerung

🎯 Wichtigste IdeeSpeichertechnologien unterscheiden sich fundamental in Zelle, Refresh, Interface und Zugriffsmuster: SRAM (6T-Flip-Flop, kein Refresh) vs. SDRAM (1T1C, Refresh, synchron, guenstig) vs. Flash (Floating Gate, nur 1->0, sektorweise loeschen).
⭐ Key
  • Flash schreibt nur 1->0; ein Bit auf '1' geht nur durch Loeschen eines ganzen Sektors. Schreiben ~16 us/Doubleword, Loeschen eines 128KB-Sektors 1-2 s.
  • NOR vs. NAND: NOR erlaubt XIP + Random Access, Code-Speicher (~1 Gbit); NAND nur Block-Zugriff, kein XIP, hohe Dichte (~1 Tbit), Basis fuer SSDs.
  • SRAM-Interface asynchron (NWE/NOE/CS), SDRAM synchron (CLK, RAS, CAS); SRAM gleichmaessige Zugriffszeit, DRAM hohe Latenz beim 1. Zugriff.
  • FMC-Anschluss (64Kx8-SRAM @ 0x6800'0000): A->ADDR, D[7:0]->DATA, NWE->WE, NOE->OE, NE->CS; Lesen CS=0/OE=0/WE=1, Schreiben CS=0/OE=1/WE=0; hoechste Adresse 0x6800'FFFF.
⚠️ StolpersteinDRAM-Fallen: Preis ist NIEDRIG (nicht hoch), aber Leistungsaufnahme ist HOCH, weil der Refresh staendig Strom braucht - genau umgekehrt zur naiven Erwartung.

Warum Speicher und Technologiewahl

Die CPU rechnet extrem schnell, aber sie braucht Daten und Programmcode. Diese muessen irgendwo gespeichert werden. Es gibt viele verschiedene Speichertechnologien — jede mit anderen Vor- und Nachteilen. Die Kunst ist, die richtige Technologie fuer den richtigen Zweck zu waehlen.

Die zwei grossen Unterscheidungen: (1) Fluechtig vs. Nicht-fluechtig — gehen die Daten bei Stromausfall verloren? (2) Schnell vs. Guenstig — schneller Speicher ist teuer, guenstiger ist langsam (deswegen gibt es die Speicherhierarchie mit Cache).

Die vier Schluesseltechnologien

Die vier wichtigsten Speichertechnologien:

SRAM: schnell, teuer, kein Refresh

1. SRAM (Static RAM) — Der schnelle, teure Speicher. Analogie: Wie ein Lichtschalter — einmal umgelegt, bleibt er in der Position (solange Strom da ist). Speicherzelle: 6 Transistoren bilden ein Flip-Flop (bistabiles Element). Haelt den Wert solange Versorgungsspannung anliegt. Kein Refresh noetig — darum "statisch". Zugriffszeit: ~5 ns (sehr schnell). Grosse Zelle → maximal ~64 Mbit Dichte. Asynchrones Interface (kein Takt, nur CS/OE/WE). Teuer pro Bit. Verwendung: Cache (L1, L2, L3), On-Chip SRAM im Mikrocontroller.

SDRAM: guenstig, gross, Refresh noetig

2. SDRAM (Synchronous Dynamic RAM) — Der guenstige, grosse Speicher. Analogie: Wie ein leckender Eimer — du fuellst Wasser rein (Ladung), aber es laeuft langsam raus. Du musst regelmaessig nachfuellen (Refresh). Speicherzelle: 1 Transistor + 1 Kondensator (1T1C). Kondensator speichert Ladung = 1 Bit. Refresh noetig! Kondensator verliert Ladung in wenigen ms (Leckstrom). Synchrones Interface (mit CLK). Hohe Latenz fuer ersten Zugriff, aber schnell fuer Burst-Zugriffe (Folgeadressen). Sehr kleine Zelle → bis 4 Gbit Dichte. Guenstig pro Bit. Verwendung: Hauptspeicher (RAM) in PCs, Smartphones, groessere Embedded Systems.

NOR Flash: Code, XIP, Random Access

3. NOR Flash — Code-Speicher. Analogie: Wie ein Buch — du kannst jede beliebige Seite direkt aufschlagen (Random Access), aber Radieren geht nur kapitelweise. Speicherzelle: Floating-Gate MOSFET. Wahlfreier Zugriff (Random Read): ~0.12 us pro Zugriff. XIP (Execute in Place): CPU kann Code direkt aus NOR Flash ausfuehren. Schreiben: nur 1→0 moeglich (~180 us/32B). Loeschen: nur sektorweise (alle Bits auf '1'): ~1 s fuer 64 KB! Endurance: ~10.000-100.000 Schreib/Loesch-Zyklen. Niedrigere Dichte (~1 Gbit). Verwendung: Firmware, Bootloader, Programmcode im Mikrocontroller.

NAND Flash: Daten, Bloecke, hohe Dichte

4. NAND Flash — Daten-Speicher. Analogie: Wie eine Lagerhalle — du kannst nur ganze Paletten (Bloecke) rein- und rausbringen, nicht einzelne Kisten. Speicherzelle: Ebenfalls Floating-Gate MOSFET, aber in Serie geschaltet. Kein wahlfreier Zugriff — nur Block-weise lesen/schreiben. Kein XIP — Code muss erst ins RAM geladen werden. Hohe Dichte (~1 Tbit). Schnell fuer grosse Datenbloecke. Verwendung: SSDs, USB-Sticks, SD-Karten, Smartphones.

  • AMAT = Hit-Time + Miss-Rate * Miss-Penalty; z.B. 2 + 0.10*100 = 12 ns (ohne Cache waeren alle Zugriffe 100 ns).

  • Schreibstrategien: Write-Through (sofort in RAM) vs. Write-Back (nur Cache + Dirty-Bit); Schreib-Miss: Write-Allocate vs. No-Write-Allocate; modern typisch Write-Back + Write-Allocate.

Was ist ein Cache und warum

Cache = kleiner, schneller Zwischenspeicher zwischen CPU und Hauptspeicher. Die CPU arbeitet viel schneller als der RAM. Ohne Cache muesste die CPU bei jedem Speicherzugriff warten. Der Cache speichert Kopien der am haeufigsten benutzten Daten, damit die CPU schnell darauf zugreifen kann.

Lokalitaetsprinzip: Temporal und Spatial

Warum funktioniert das? Lokalitaetsprinzip: Programme greifen nicht zufaellig auf den Speicher zu, sondern folgen zwei Mustern.

Zeitliche Lokalitaet (Temporal Locality): Wenn du auf eine Adresse zugreifst, wirst du wahrscheinlich bald wieder auf dieselbe Adresse zugreifen. Beispiel: Eine Schleifenvariable i wird bei jedem Durchlauf gelesen und geschrieben.

Raeumliche Lokalitaet (Spatial Locality): Wenn du auf eine Adresse zugreifst, wirst du wahrscheinlich bald auf benachbarte Adressen zugreifen. Beispiel: Ein Array a[0], a[1], a[2], ... wird der Reihe nach durchlaufen.

for (i = 0; i < 100000; i++) {   // i → temporal locality
    a[i] = b[i];                  // a[i], a[i+1] → spatial locality
}

Speicherhierarchie

Speicherhierarchie: Je naeher am Prozessor, desto schneller, kleiner und teurer.

L1 Cache ist oft "Harvard"-Architektur (getrennte Caches fuer Daten und Instruktionen). Ab L2 ist es "Von Neumann" (gemeinsam).

Cache-Mechanik: Bloecke und Cache-Lines

Cache-Mechanik — Bloecke: Der gesamte Speicher wird in Bloecke fester Groesse aufgeteilt. Ein Block ist die kleinste Einheit, die zwischen Cache und RAM hin- und herkopiert wird.

Beispiel: 16-Bit Adressraum (0x0000 - 0xFFFF), Blockgroesse B = 4 Bytes: Block 0 = Adressen 0x0000-0x0003 (4 Bytes), Block 1 = 0x0004-0x0007, Block 2 = 0x0008-0x000B, usw.

Blocknummer einer Adresse: BlockNr = Adresse / B (ganzzahlig, also die oberen Bits). Offset innerhalb eines Blocks: Offset = Adresse mod B (die unteren Bits).

Cache-Line: Der Cache besteht aus m Cache-Lines. Jede Line speichert genau einen Block: Line = [Valid-Bit (1 Bit) | Tag (t Bit) | Daten (B Bytes)].

Valid-Bit (v): 1 = diese Line enthaelt gueltige Daten, 0 = leer/ungueltig. Tag: Identifiziert WELCHER Block in dieser Line gespeichert ist. Daten: Die eigentlichen Bytes (Kopie aus dem RAM).

Cache-Kapazitaet = m * B Bytes (Anzahl Lines * Bytes pro Line).

Cache Hit: CPU fragt Adresse an, Block ist im Cache, Daten werden sofort geliefert (schnell). Cache Miss: CPU fragt Adresse an, Block ist NICHT im Cache, Block muss erst aus RAM geladen werden (langsam), wird dann in eine Cache-Line kopiert.

Adressaufteilung: Tag, Index, Offset

Adressaufteilung (der Kern des Themas): Die CPU gibt eine n-Bit Adresse aus. Diese wird in Felder aufgeteilt, um den Cache zu durchsuchen. Wie genau aufgeteilt wird, haengt von der Cache-Organisation ab.

Es gibt immer einen Offset (die untersten Bits), der angibt, welches Byte innerhalb des Blocks gemeint ist: Offset-Bits = log2(B). Beispiel: B = 4 Bytes → Offset = log2(4) = 2 Bit (Werte 00, 01, 10, 11 = Byte 0, 1, 2, 3 im Block). Die restlichen Bits identifizieren den Block. Wie diese Bits verwendet werden, ist der Unterschied zwischen den drei Cache-Organisationen.

Fully Associative

Organisation 1 — Fully Associative (Vollassoziativ): Jeder Block kann in JEDE Cache-Line gespeichert werden (maximale Freiheit). Adressaufteilung: [Tag (n - log2(B)) Bit | Offset (log2(B)) Bit] — es gibt keinen Index, der Tag ist die komplette Blocknummer.

Kochrezept Fully Associative: Gegeben n-Bit Adresse, B Bytes pro Block. (1) Offset = log2(B) Bit. (2) Tag = n - Offset Bit. Fertig, kein Index.

Beispiel Fully Associative: 16-Bit Adresse, B = 4 Bytes, m = 4 Lines. Offset = log2(4) = 2 Bit. Tag = 16 - 2 = 14 Bit. Adresse 0x0005 = 0000 0000 0000 01|01 → Tag = 0000 0000 0000 01 (= Block 1), Offset = 01 (= Byte 1 im Block). Adresse 0x0007 = 0000 0000 0000 01|11 → Tag = Block 1 (gleicher Block), Offset = 11 (= Byte 3 im Block).

Suche bei Fully Associative: Der Tag der Adresse wird gleichzeitig mit allen m Lines verglichen → braucht m Komparatoren. Vorteile: Beste Hit-Rate, keine Conflict Misses. Nachteile: Teuer (m Komparatoren), langsam bei grossem m.

Direct Mapped

Organisation 2 — Direct Mapped (Direkt Abgebildet): Jeder Block kann nur in EINE bestimmte Cache-Line. Welche? LineNr = BlockNr mod m. Adressaufteilung: [Tag | Index (log2(m)) Bit | Offset (log2(B)) Bit]. Der Index zeigt direkt auf die Cache-Line, der Tag identifiziert, welcher Block dort gespeichert ist.

Kochrezept Direct Mapped: Gegeben n-Bit Adresse, B Bytes pro Block, m Lines. (1) Offset = log2(B) Bit. (2) Index = log2(m) Bit. (3) Tag = n - Index - Offset Bit.

Beispiel Direct Mapped: 16-Bit Adresse, B = 4 Bytes, m = 256 Lines. Offset = log2(4) = 2 Bit. Index = log2(256) = 8 Bit. Tag = 16 - 8 - 2 = 6 Bit. Ergebnis: [Tag: 6 Bit | Index: 8 Bit | Offset: 2 Bit].

Suche bei Direct Mapped: Index → direkt zur Line → nur 1 Tag-Vergleich → 1 Komparator. Vorteile: Einfach, schnell, billig. Nachteile: Conflict Misses — zwei Bloecke mit gleichem Index verdraengen sich gegenseitig, obwohl der Cache noch Platz haette. Beispiel: Block 0 → Line 0 (0 mod 256 = 0), Block 256 → Line 0 (256 mod 256 = 0). Greift das Programm abwechselnd auf Block 0 und Block 256 zu, gibt es staendig Misses ("Thrashing").

N-Way Set Associative

Organisation 3 — N-Way Set Associative (N-Wege Satz-Assoziativ): Kompromiss. Der Cache wird in Saetze (Sets) aufgeteilt. Jeder Satz hat n Lines ("n-Way"). Ein Block geht in genau einen Satz (wie Direct Mapped), aber innerhalb des Satzes in jede der n Lines (wie Fully Associative). Anzahl Saetze: s = m / n. SetNr = BlockNr mod s. Adressaufteilung: [Tag | Set-Index (log2(s)) Bit | Offset (log2(B)) Bit].

Kochrezept N-Way Set Associative: Gegeben n-Bit Adresse, B Bytes pro Block, m Lines, n Ways. (1) Offset = log2(B) Bit. (2) s = m / n (Anzahl Saetze). (3) Set-Index = log2(s) Bit. (4) Tag = n_addr - Set-Index - Offset Bit.

Beispiel N-Way: 16-Bit Adresse, B = 4 Bytes, m = 256 Lines, n = 2 Ways. Offset = log2(4) = 2 Bit. s = 256 / 2 = 128 Saetze. Set-Index = log2(128) = 7 Bit. Tag = 16 - 7 - 2 = 7 Bit. Ergebnis: [Tag: 7 Bit | Set-Index: 7 Bit | Offset: 2 Bit].

Suche bei N-Way: Set-Index → zum Satz → n Komparatoren (einen pro Way). Vorteile: Weniger Conflict Misses als Direct Mapped. Nachteile: n Komparatoren (mehr als DM, weniger als FA).

Zusammenhang der drei Organisationen: Es ist das gleiche Konzept mit unterschiedlichen Parametern.

Die drei C's: Cold, Capacity, Conflict

Cache Misses — die drei C's: Wenn der CPU-Zugriff nicht im Cache ist (Miss), gibt es drei moegliche Gruende.

Cold Miss (Compulsory Miss): Erster Zugriff auf einen Block, er war noch nie im Cache. Unvermeidbar, auch bei unendlich grossem Cache. Kann durch Prefetching reduziert werden (Block vorab laden).

Capacity Miss: Der Working Set (alle Daten, die das Programm gerade braucht) ist groesser als der Cache. Tritt auch bei Fully Associative auf. Loesung: groesseren Cache verwenden.

Conflict Miss: Zwei Bloecke konkurrieren um die gleiche Line/Set, obwohl noch andere Lines frei waeren. Tritt nur bei Direct Mapped und N-Way auf (NICHT bei Fully Associative). Loesung: hoehere Assoziativitaet (mehr Ways).

Wichtig: Cold Misses sind unvermeidbar (groesserer Cache hilft nicht). Conflict Misses werden nur durch hoehere Assoziativitaet geloest, nicht durch mehr Kapazitaet (es sei denn, man geht zu Fully Associative).

AMAT, Hit Rate und Miss Rate

Cache-Performance — AMAT (Average Memory Access Time): AMAT = Hit Time + Miss Rate * Miss Penalty. Hit Time = wie lange ein Cache-Hit dauert (z.B. 2 ns). Miss Rate = Anteil der Zugriffe, die ein Miss sind (z.B. 10% = 0.1). Miss Penalty = wie lange es dauert, den Block aus dem RAM zu laden (z.B. 100 ns).

Beispiel AMAT: Hit Time = 2 ns, Miss Rate = 10%, Miss Penalty = 100 ns → AMAT = 2 + 0.10 * 100 = 12 ns. Ohne Cache waere jeder Zugriff 100 ns, mit Cache nur 12 ns (8x schneller). Weiteres Beispiel: Hit Time = 4 ns, Miss Rate = 5%, Miss Penalty = 200 ns → AMAT = 4 + 0.05 * 200 = 14 ns. Schon 5% Miss Rate verursacht eine Verdreifachung gegenueber der Hit Time, Miss Rate klein zu halten ist entscheidend.

⭐ KeyDie Miss Rate dominiert die AMAT - schon kleine Miss-Raten kosten viel, da die Miss Penalty viel groesser ist als die Hit Time.

Hit Rate und Miss Rate: Hit Rate = Hits / (Hits + Misses), Miss Rate = 1 - Hit Rate = Misses / (Hits + Misses).

Typische Kombinationen: Write-Back + Write-Allocate → moderne L1/L2 Caches (schnell). Write-Through + No-Write-Allocate → einfachere Systeme.

Cache-freundlicher Code (Row-Major)

Cache-freundlicher Code — Array-Layout in C: C speichert 2D-Arrays zeilenweise (Row-Major Order) im Speicher.

int A[3][4];
// Im Speicher: A[0][0] A[0][1] A[0][2] A[0][3] A[1][0] A[1][1] ...
//              ←────── Zeile 0 ──────→ ←────── Zeile 1 ──────→

Cache-freundlicher Zugriff:

// GUT: i aussen, j innen → Zugriff auf aufeinanderfolgende Adressen
for (int i = 0; i < N; i++)          // Zeilenweise
    for (int j = 0; j < M; j++)      // Spaltenweise (Schritt = 1 Element)
        sum += A[i][j];

Warum gut? A[i][0] und A[i][1] liegen direkt nebeneinander im Speicher. Wenn der Cache A[i][0] laedt, sind A[i][1], A[i][2], A[i][3] im gleichen Block, sie sind sofort im Cache (Spatial Locality).

Cache-unfreundlicher Zugriff:

// SCHLECHT: j aussen, i innen → Zugriff springt ueber ganze Zeilen
for (int j = 0; j < M; j++)          // Spaltenweise
    for (int i = 0; i < N; i++)      // Zeilenweise (Schritt = M Elemente!)
        sum += A[i][j];

Warum schlecht? A[0][j] und A[1][j] sind M * sizeof(int) Bytes auseinander. Bei grossen Arrays liegt jeder Zugriff in einem anderen Block → jeder Zugriff ist ein Cache Miss.

Leistungsunterschied: Bei grossen Arrays bis zu 5x Speedup durch die richtige Schleifen-Reihenfolge. Merkregel: Die innerste Schleife sollte den Index veraendern, der den kleinsten Speicherabstand zwischen aufeinanderfolgenden Zugriffen erzeugt. Bei C-Arrays (A[i][j]) ist das immer j (der rechte Index).

Was ist eine State Machine?

Eine State Machine modelliert ein System, das immer in genau einem Zustand ist und je nach Zustand unterschiedlich auf Eingaben reagiert. Beispiel Getraenkeautomat: Zustaende "wartet auf Geld", "Geld eingeworfen", "Getraenk wird ausgegeben". Wenn er "wartet auf Geld" ist und eine Muenze eingeworfen wird, wechselt er zu "Geld eingeworfen". Wenn er "wartet auf Geld" ist und der Ausgabe-Knopf gedrueckt wird, passiert nichts (ignoriert). Wenn er "Geld eingeworfen" ist und der Knopf gedrueckt wird, wechselt er zu "Getraenk wird ausgegeben". Kernidee: Das gleiche Event hat je nach Zustand eine andere Wirkung.

Formale Definition einer FSM

Eine Finite State Machine (FSM) besteht formal aus: einer endlichen Menge von Zustaenden (States), einer endlichen Menge von Ereignissen (Events), Uebergaengen (Transitions: Zustand + Event → neuer Zustand + Aktionen) und einem Anfangszustand (Initial State).

Warum FSM in Embedded Systems?

Embedded Systems sind reaktive Systeme: Sie reagieren staendig auf Events von aussen (Tastendruck, Timer-Ablauf, Daten empfangen). Ohne State Machine wird der Code schnell unuebersichtlich mit vielen verschachtelten if-else und globalen Flags. Eine FSM strukturiert das Verhalten sauber. Typische Anwendungen: Waschmaschinen, Getraenkeautomaten, Heizungssteuerungen, Kommunikationsprotokolle (HTTP, TCP), Benutzereingabe-Validierung (PIN-Eingabe), Ampelsteuerungen.

Hardware-FSM vs. Software-FSM

Hardware-FSM vs. Software-FSM: In CT1 wurden FSMs als Hardware kennengelernt — Flip-Flops speichern den Zustand, kombinatorische Logik berechnet den naechsten Zustand bei jedem Takt. In Software funktioniert das anders.

Warum event-getrieben? In Hardware ist es gratis, alle Eingaenge bei jedem Takt auszuwerten (parallele Logik). In Software muesste die CPU bei jedem Takt alle Eingaenge pruefen, was CPU-Zeit verschwendet. Besser: Nur reagieren wenn ein Event kommt.

Moore vs. Mealy

Moore-Automat: Ausgabe haengt NUR vom aktuellen Zustand ab. Die Aktionen werden beim Eintreten in einen Zustand ausgefuehrt (Entry-Actions). Egal welches Event den Zustand ausgeloest hat, die Ausgabe ist immer die gleiche. Beispiel: Zustand "GRUEN" → Aktion gruene LED einschalten. Egal ob man von ROT oder von GELB nach GRUEN kam, die LED ist gruen.

Mealy-Automat: Ausgabe haengt vom Zustand UND vom Event ab. Die Aktionen werden bei der Transition ausgefuehrt. Das gleiche Event kann in verschiedenen Zustaenden verschiedene Aktionen ausloesen. Beispiel: Event "Knopf gedrueckt" — in Zustand OFF → Aktion LED an (Transition OFF→ON), in Zustand ON → Aktion LED aus (Transition ON→OFF).

C-Implementierung: Switch-Case

C-Implementierung Methode 1: Switch-Case (am haeufigsten in Pruefungen):

typedef enum { REST, WASH, RINSE, DRY } State;
typedef enum { EV_START, EV_STOP, EV_TIMEOUT } Event;

State state = REST;  // Anfangszustand

void fsm_init(void) {
    water_off(); shampoo_off(); air_off();
    state = REST;
}

void fsm_handle_event(Event ev) {
    switch (state) {
        case REST:
            if (ev == EV_START) {
                water_on(); shampoo_on(); timer_start();
                state = WASH;
            }
            break;
            
        case WASH:
            if (ev == EV_TIMEOUT) {
                shampoo_off(); timer_start();
                state = RINSE;
            } else if (ev == EV_STOP) {
                shampoo_off(); water_off();
                state = REST;
            }
            break;
            
        case RINSE:
            if (ev == EV_TIMEOUT) {
                water_off(); air_on(); timer_start();
                state = DRY;
            } else if (ev == EV_STOP) {
                water_off();
                state = REST;
            }
            break;
            
        case DRY:
            if (ev == EV_TIMEOUT || ev == EV_STOP) {
                air_off();
                state = REST;
            }
            break;
    }
}

Wie liest man das? Aeusserer switch = aktueller Zustand. Innere if/switch = welches Event. Dann: Aktionen ausfuehren + neuen Zustand setzen.

C-Implementierung: Transition Table

C-Implementierung Methode 2: Transition Table:

typedef void (*ActionFunc)(void);
typedef struct {
    State next;
    ActionFunc action;
} Transition;

// Hilfsfunktionen fuer kombinierte Aktionen
void start_wash(void)  { water_on(); shampoo_on(); timer_start(); }
void wash_to_rinse(void) { shampoo_off(); timer_start(); }
void rinse_to_dry(void)  { water_off(); air_on(); timer_start(); }
void stop_wash(void)   { shampoo_off(); water_off(); }
void stop_rinse(void)  { water_off(); }
void stop_dry(void)    { air_off(); }

Transition table[4][3] = {
//                    EV_START          EV_STOP           EV_TIMEOUT
/* REST  */ { {WASH, start_wash},  {REST, NULL},     {REST, NULL}      },
/* WASH  */ { {WASH, NULL},        {REST, stop_wash},{RINSE,wash_to_rinse}},
/* RINSE */ { {RINSE, NULL},       {REST, stop_rinse},{DRY, rinse_to_dry}},
/* DRY   */ { {DRY, NULL},         {REST, stop_dry}, {REST, stop_dry}  },
};

void fsm_handle_event(Event ev) {
    Transition t = table[state][ev];
    if (t.action) t.action();
    state = t.next;
}

Vorteil Transition Table: Alle Transitionen auf einen Blick in der Tabelle, leicht erweiterbar. Nachteil: Braucht extra Hilfsfunktionen fuer kombinierte Aktionen.

Run-to-Completion

Run-to-Completion — die wichtigste Regel: Ein Event wird KOMPLETT verarbeitet (alle Aktionen + Zustandswechsel), bevor das naechste Event bearbeitet wird.

Event-Queue: [EV_START, EV_TIMEOUT, EV_STOP]

1. EV_START verarbeiten:  REST → WASH    (water_on, shampoo_on, timer_start)
   ← FERTIG, erst jetzt naechstes Event
2. EV_TIMEOUT verarbeiten: WASH → RINSE  (shampoo_off, timer_start)
   ← FERTIG
3. EV_STOP verarbeiten: RINSE → REST    (water_off)
   ← FERTIG

Warum Run-to-Completion? Garantiert, dass das System nach jeder Event-Verarbeitung in einem konsistenten Zustand ist. Keine "halb ausgefuehrten" Transitionen.

⚠️ StolpersteinISRs duerfen Events nur in die Queue schreiben, NICHT die FSM direkt aufrufen - sonst bricht Run-to-Completion und der Zustand wird inkonsistent.

Event-Driven mit Interrupts

Event-Driven Architektur (mit Interrupts): In der Praxis kommen Events von Interrupts. Die ISR schreibt das Event in eine Queue, die Main-Loop verarbeitet es.

// Event-Queue
volatile Event event_queue[16];
volatile uint8_t q_head = 0, q_tail = 0;

// ISRs: Nur Event eintragen, NICHT verarbeiten!
void TIM3_IRQHandler(void) {
    TIM3->SR &= ~0x01;
    event_queue[q_tail++] = EV_TIMEOUT;
    q_tail %= 16;
}

void EXTI0_IRQHandler(void) {
    EXTI->PR = (1 << 0);
    event_queue[q_tail++] = EV_START;
    q_tail %= 16;
}

// Main-Loop: Events aus Queue holen und FSM fuettern
int main(void) {
    fsm_init();
    init_peripherals();
    
    while (1) {
        if (q_head != q_tail) {           // Event vorhanden?
            Event ev = event_queue[q_head++];
            q_head %= 16;
            fsm_handle_event(ev);          // FSM verarbeitet
        }
    }
}

Erklaerung

🎯 Wichtigste IdeeDie Impact-Formel quantifiziert, wie viel CPU-Zeit ein Interrupt frisst: Impact[%] = f_INT * t_ISR * 100%, mit f_INT = Datenrate/Puffergroesse und t_ISR = ISR-Zyklen/f_CPU.
⭐ Key
  • Beispiel: 1 MHz CPU, 16 kbit/s, 32-Bit-Puffer, 100 CLK ISR -> f_INT = 16000/32 = 500 Hz, t_ISR = 100/1MHz = 100 us, Impact = 500 * 100us = 5%; Max. Datenrate (100%) = 32 / 100us = 320 kbit/s.
  • Bei mehreren ISRs addieren sich die Anteile: Impact_ges = Summe(f_i * t_i) * 100%.
  • Drei Ebenen zum Aktivieren: 1) Peripheral (DIER/CR2, z.B. UIE/TXEIE/EOCIE), 2) NVIC (ISER[0] |= (1<<IRQ)), 3) Global (__enable_irq()); IRQ >= 32 in ISER[1] mit Bit = IRQ-32.
  • Ablauf: Hardware sichert automatisch 8 Register (xPSR, PC, LR, R12, R3-R0); Latenz ~12-25 Zyklen.
⚠️ StolpersteinFlag-Reset MUSS in der ISR ZUERST erfolgen (TIMx->SR &= ~0x01) - sonst sofortige Wiederausloesung; geteilte Variablen brauchen volatile, sonst sieht die Main-Loop die ISR-Aenderung nicht.

Was ist ein Interrupt? Ein Interrupt ist ein Hardware-Signal, das die CPU aus dem normalen Programm unterbricht, um etwas Dringendes zu erledigen. Analogie: Du liest ein Buch (= main-Programm), ploetzlich klingelt dein Handy (= Interrupt-Signal). Du legst ein Lesezeichen rein (= Register sichern), gehst ans Telefon (= ISR ausfuehren), legst auf, und liest dort weiter, wo du aufgehoert hast (= Register wiederherstellen).

Warum braucht man Interrupts? Peripherie-Geraete (SPI, UART, ADC, Timer, GPIO) muessen der CPU mitteilen, wenn etwas passiert ist: "SPI hat Daten gesendet, bereit fuer naechste" (TXE-Flag), "UART hat ein Byte empfangen" (RXNE-Flag), "ADC Wandlung fertig" (EOC-Flag), "Timer abgelaufen" (UIF-Flag), "Taster gedrueckt" (GPIO EXTI). Ohne Interrupts muesste die CPU staendig alle diese Flags abfragen (Polling). Mit Interrupts wird die CPU automatisch benachrichtigt.

Polling vs. Interrupt — Die zwei Methoden

Polling (Abfragen): Die CPU fragt in einer Schleife staendig die Status-Register aller Peripherie ab:

while (1) {
    if (spi_is_txe_set()) {        // SPI bereit?
        spi_write_data(...);
    }
    if (uart_is_rxne_set()) {      // UART Daten da?
        uart_data = uart_read_data();
    }
    if (adc_is_eoc()) {            // ADC fertig?
        adc_data = adc_read_data();
    }
}

Polling-Vorteile: Einfach und verstaendlich; deterministisch (kein unerwartetes Unterbrechen); keine Interrupt-Logik noetig; sehr schnelle Reaktion wenn nur ein Geraet abgefragt wird.

Polling-Nachteile: CPU ist staendig beschaeftigt (Busy-Wait), auch wenn nichts passiert; verschwendet Rechenzeit; lange Reaktionszeiten wenn viele Geraete abgefragt werden; CPU kann nicht schlafen (hoher Stromverbrauch).

Interrupt-Driven I/O: Die CPU wird automatisch benachrichtigt. Sie kann dazwischen andere Dinge tun oder schlafen:

// ISR wird automatisch von Hardware aufgerufen
void USART1_IRQHandler(void) {
    if (USART1->SR & USART_SR_RXNE) {
        char c = USART1->DR;   // Daten lesen (cleart RXNE)
        process(c);
    }
}

// Hauptschleife kann andere Arbeit machen
int main(void) {
    init_usart();
    while (1) {
        do_other_work();   // CPU ist frei!
    }
}

Interrupt-Vorteile: CPU-effizient (arbeitet nur wenn noetig); schnelle Reaktion auf Events; CPU kann schlafen (Energiesparen).

Interrupt-Nachteile: Komplexer (ISR-Sicherheit, Race Conditions, volatile); Latenz durch Overhead (Register sichern/wiederherstellen); schwerer zu debuggen.

Wie funktioniert ein Interrupt? (Der Ablauf)

Die 5 Schritte:

  1. INTERRUPT-ANFORDERUNG Hardware setzt Flag im Status-Register (z.B. TIM3_SR.UIF = 1) Wenn Interrupt-Enable-Bit gesetzt → IRQ-Leitung geht auf HIGH
  2. NVIC EMPFAENGT IRQ NVIC prueft: Ist dieser IRQ aktiviert (ISER)? Hat er hoehere Prioritaet als das was gerade laeuft?
  3. HARDWARE SICHERT KONTEXT (automatisch!) CPU sichert 8 Register auf den Stack: xPSR, PC, LR, R12, R3, R2, R1, R0 Das dauert ~12 Taktzyklen
  4. ISR WIRD AUSGEFUEHRT CPU springt zur ISR-Adresse (aus der Vektortabelle) ISR laeuft → Flag loeschen, Daten verarbeiten
  5. RUECKKEHR Hardware stellt die 8 Register vom Stack wieder her CPU setzt normales Programm fort

Was wird automatisch gesichert?

R4-R11 werden NICHT automatisch gesichert. Wenn die ISR diese Register benutzt, muss der Compiler sie in der ISR sichern/wiederherstellen (macht er automatisch).

Interrupt-Konfiguration: Die drei Ebenen

Ein Interrupt muss an drei Stellen aktiviert werden, bevor er funktioniert:

Ebene 1: Im Peripheral — Interrupt-Enable-Bit. Jedes Peripheral hat ein Interrupt Enable Register (IER) oder einzelne Enable-Bits:

TIM3->DIER |= (1 << 0);    // UIE: Update Interrupt Enable
SPI1->CR2  |= (1 << 7);    // TXEIE: TX Buffer Empty Interrupt Enable
ADC1->CR1  |= (1 << 5);    // EOCIE: End of Conversion Interrupt Enable

Wichtig: Das Flag im Status-Register (z.B. UIF) wird von der Hardware gesetzt und muss von der Software geloescht werden. Das Enable-Bit bestimmt nur, ob das Flag auch einen IRQ ausloest.

Ebene 2: Im NVIC — IRQ aktivieren und Prioritaet setzen.

// TIM3 = IRQ 29 → liegt in ISER[0], Bit 29
NVIC->ISER[0] |= (1 << 29);    // IRQ 29 aktivieren

// Prioritaet setzen (STM32: nur obere 4 Bit von 8 → 16 Stufen)
NVIC->IPR[29] = (2 << 4);      // Prioritaet 2 (0 = hoechste)

Ebene 3: Global — PRIMASK.

__enable_irq();    // PRIMASK = 0 → alle IRQs erlaubt (Standard)
__disable_irq();   // PRIMASK = 1 → alle IRQs gesperrt

NVIC — Nested Vectored Interrupt Controller

Der NVIC ist die zentrale Verwaltung aller Interrupts. Er entscheidet, welcher Interrupt wann ausgefuehrt wird. Nested: Hoeher-priore Interrupts koennen niedrigere unterbrechen. Vectored: Jeder Interrupt hat einen festen Eintrag in der Vektortabelle mit der Adresse der ISR. Bis zu 240 IRQ-Quellen.

Die Impact-Formel (PRUEFUNGSRELEVANT!)

Impact [%] = f_INT * t_ISR * 100%

Was bedeutet das? Wieviel Prozent der CPU-Zeit wird fuer Interrupt-Bearbeitung verwendet. f_INT = Wie oft kommt der Interrupt pro Sekunde? [Hz]. t_ISR = Wie lange dauert die ISR? [Sekunden].

Wie berechne ich f_INT? Die Interrupt-Frequenz haengt von der Datenquelle ab:

f_INT = Datenrate / Puffergroesse
Beispiel: Schnittstelle mit 16 kbit/s, Puffer = 32 Bit
→ f_INT = 16'000 bit/s / 32 bit = 500 Hz (500 Interrupts pro Sekunde)
Beispiel: UART mit 230'400 Baud, 8-Bit Daten
→ f_INT = 230'400 / 8 = 28'800 Hz
Beispiel: Timer mit 1 kHz Overflow
→ f_INT = 1000 Hz

Wie berechne ich t_ISR? Die ISR-Zeit haengt von der Anzahl Taktzyklen und der CPU-Frequenz ab:

t_ISR = Zyklen / f_CPU
Beispiel: ISR braucht 100 Zyklen, CPU laeuft mit 1 MHz
→ t_ISR = 100 / 1'000'000 = 100 us = 0.0001 s
Beispiel: ISR braucht 1000 Zyklen, CPU laeuft mit 168 MHz
→ t_ISR = 1000 / 168'000'000 ≈ 6 us

Mehrere Interrupt-Quellen:

Impact_gesamt = SUM(f_INTi * t_ISRi) * 100%
Beispiel:
Timer: 1 kHz, 10 us → 1000 * 10e-6 = 0.01 = 1%
USART: 28.8 kHz, 6 us → 28800 * 6e-6 = 0.173 = 17.3%
ADC: 10 kHz, 5 us → 10000 * 5e-6 = 0.05 = 5%
Gesamt: 23.3%

Interrupt-Latenz

Interrupt-Latenz = Zeit vom Auftreten des Interrupt-Events bis zum ersten Befehl der ISR.

Hardware-Latenz (unvermeidbar): Aktuelle Instruktion abschliessen (1-12 Zyklen je nach Instruktion); 8 Register auf Stack pushen (~12 Zyklen); ISR-Adresse aus Vektortabelle laden. Gesamt: ~12-25 Zyklen (bei 168 MHz: ~72-149 ns).

Software-Latenz (vermeidbar): Hoeher-priore ISR laeuft gerade → muss warten; PRIMASK = 1 (Interrupts global gesperrt) → muss warten; mehrere Quellen teilen eine IRQ-Leitung → Polling in ISR noetig.

Pre-Emption (Vorrangunterbrechung): Ein Interrupt mit hoeherer Prioritaet kann eine laufende ISR unterbrechen:

Beispiel: IRQ_A (Prio 2, mittel), IRQ_B (Prio 1, hoch)

  IRQ_A kommt → ISR_A beginnt
    Waehrend ISR_A laeuft: IRQ_B kommt (hoehere Prio!)
    → ISR_A wird pausiert
    → ISR_B laeuft
    → ISR_B fertig
    → ISR_A wird fortgesetzt
  → main() laeuft weiter

Problem: Hoeher-priore Interrupts erhoehen die Latenz fuer niederpriore. Wenn ISR_A hoch-prior ist und lange dauert, muessen alle anderen Interrupts warten.

Latenz Management: ISRs kurz halten

Das Problem: Eine ISR die auf Output wartet (z.B. "warte bis SPI bereit ist") blockiert alle niederprioren Interrupts:

// SCHLECHT: Warteschleife in ISR!
void SPI_IRQHandler(void) {
    data = read_input();
    process(data);
    while (!(SPI->SR & TXE)) {}  // Warten auf SPI → blockiert!
    SPI->DR = result;
}

Die Loesung: FIFO-Queue. ISR macht nur das Noetigste (Daten lesen, in Queue schreiben). Die Verarbeitung passiert in der Main-Schleife:

// GUT: ISR ist kurz und deterministisch
void INPUT_IRQHandler(void) {
    uint32_t data = read_input();     // Daten von Hardware lesen
    queue_enqueue(&input_queue, data); // In Queue schreiben
    // FERTIG! Kein Warten, keine Verarbeitung
}

int main(void) {
    while (1) {
        if (queue_has_data(&input_queue)) {
            uint32_t data = queue_dequeue(&input_queue);
            uint32_t result = process(data);
            // Output erst wenn bereit:
            if (output_ready()) {
                write_output(result);
            }
        }
    }
}

Vorteile: ISR ist kurz → niedrige Latenz fuer alle Interrupts; kein Busy-Wait in ISR; Main-Loop kann mehrere Queues bedienen; Entkopplung von Input-Rate und Output-Rate.

Interrupt-Driven FSM: Die Queue-Architektur passt perfekt zu State Machines:

// Mehrere ISRs schreiben Events in eine Queue
void TIM3_IRQHandler(void) {
    TIM3->SR &= ~0x01;
    queue_enqueue(&event_queue, EVENT_TIMEOUT);
}
void EXTI0_IRQHandler(void) {
    EXTI->PR = (1 << 0);
    queue_enqueue(&event_queue, EVENT_BUTTON);
}

// Main-Loop: FSM verarbeitet Events
int main(void) {
    fsm_init();
    peripherals_init();
    while (1) {
        Event e = get_event_from_queue();
        if (e) {
            fsm_handle_event(e);  // State Machine verarbeitet
        }
    }
}

ISR Best Practices (die goldenen Regeln)

1. Flag IMMER ZUERST loeschen.

void TIM3_IRQHandler(void) {
    TIM3->SR &= ~0x01;    // UIF-Flag loeschen — ERSTE ZEILE!
    // ... Rest der ISR
}

Warum? Wenn du das Flag nicht loeschst, denkt die Hardware der Interrupt ist noch aktiv → sofort erneute Ausloesung → Endlosschleife! Warum ZUERST? Wenn die ISR laenger dauert und ein neuer Interrupt waehrend der ISR kommt, wird er korrekt als "pending" registriert und nach der aktuellen ISR bearbeitet.

2. Geteilte Variablen als volatile deklarieren.

volatile uint32_t tick_count = 0;  // volatile = Compiler darf nicht optimieren

void TIM3_IRQHandler(void) {
    TIM3->SR &= ~0x01;
    tick_count++;           // ISR schreibt
}

int main(void) {
    while (tick_count < 1000) {  // main liest → muss volatile sein!
        // warte
    }
}

Warum? Ohne volatile koennte der Compiler tick_count in ein CPU-Register laden und nie wieder aus dem Speicher lesen → die Aenderung durch die ISR wuerde "unsichtbar".

3. Kritische Abschnitte schuetzen.

volatile uint32_t shared_data;

// RICHTIG: Interrupts sperren waehrend kritischem Zugriff
__disable_irq();          // PRIMASK = 1
uint32_t local = shared_data;  // Lesen
local += 1;
shared_data = local;      // Schreiben
__enable_irq();           // PRIMASK = 0

Warum? Ohne Sperre koennte ein Interrupt die Variable zwischen Lesen und Schreiben aendern → Race Condition!

4. ISR so kurz wie moeglich. Nur Daten lesen/schreiben, Flag setzen; Verarbeitung in Main-Loop; kein while-Warten in ISR!; kein malloc/free in ISR.

Komplettes Timer-Interrupt-Setup (Kochrezept)

// 1. Timer-Clock aktivieren
RCC->APB1ENR |= (1 << 1);      // TIM3EN

// 2. Timer konfigurieren
TIM3->PSC = 8399;               // Prescaler: 84MHz/8400 = 10kHz
TIM3->ARR = 9999;               // Reload: 10000/10kHz = 1s

// 3. Interrupt im Peripheral aktivieren (Ebene 1)
TIM3->DIER |= (1 << 0);        // UIE = Update Interrupt Enable

// 4. Interrupt im NVIC aktivieren (Ebene 2)

    // ... deine Aktion

Aufgaben & Selbsttest

Aufgabe 1: Ein Prozessorsystem mit 1 MHz Takt empfaengt ueber ein Peripheriegeraet Daten mit 16 kbit/s. Das Geraet puffert 32 Bit und loest einen Interrupt aus wenn die Daten abholbereit sind. Die ISR braucht im Schnitt 100 Clockzyklen (inkl. Aufruf und Ruecksprung). a) Wieviel Prozent der CPU-Zeit braucht das System fuer Interrupts? b) Bei welcher Datenrate waere die CPU 100% ausgelastet? c) Bei 90% Auslastung gehen trotzdem Daten verloren. Warum?

Loesung anzeigen

Aufgabe 1:

a) Wieviel Prozent der CPU-Zeit braucht das System fuer Interrupts?

Schritt 1: Interrupt-Frequenz berechnen:

f_INT = Datenrate / Puffergroesse
= 16'000 bit/s / 32 bit
= 500 Hz

→ Alle 2 ms kommt ein Interrupt (1/500 = 0.002 s).

Schritt 2: ISR-Zeit berechnen:

t_ISR = Zyklen / f_CPU
= 100 / 1'000'000
= 100 us = 0.0001 s

→ Jede ISR dauert 100 Mikrosekunden.

Schritt 3: Impact berechnen:

Impact = f_INT * t_ISR * 100%
= 500 Hz * 100 us * 100%
= 500 * 0.0001 * 100%
= 0.05 * 100%
= 5%

Antwort: Das System verbringt 5% seiner Rechenzeit mit Interrupt-Behandlung. 95% bleiben fuer das Hauptprogramm.

b) Bei welcher Datenrate waere die CPU 100% ausgelastet? Denkweg: Impact = 100% → nach x aufloesen.

(x / 32 bit) * 100 us * 100% = 100%
x / 32 * 0.0001 = 1
x / 32 = 10'000
x = 320'000 bit/s = 320 kbit/s

Antwort: Ab 320 kbit/s wuerde die CPU nur noch Interrupts verarbeiten.

c) Bei 90% Auslastung gehen trotzdem Daten verloren. Warum? Die angegebenen 100 Clockzyklen sind ein Durchschnittswert. Die tatsaechliche ISR-Dauer schwankt, weil: die Interrupt-Latenz variiert je nach Instruktion bei der unterbrochen wird (manche Instruktionen brauchen laenger zum Abschliessen als andere, z.B. SDIV vs. einfache ADD); die Anzahl Instruktionen in der ISR kann von den verarbeiteten Daten abhaengen; bei hoher Auslastung kann es passieren, dass eine ISR etwas laenger dauert als ueblich und der naechste Interrupt schon kommt bevor die Daten abgeholt sind → Datenverlust. Kernaussage: Durchschnittlich 90% ist nicht dasselbe wie "immer unter 100%". Einzelne Spitzenwerte koennen trotzdem zu Ueberlastung fuehren.

APB — Advanced Peripheral Bus — langsamerer Peripheriebus (APB1 42/84 MHz, APB2 84 MHz).

CPLD — Complex Programmable Logic Device — dekodiert auf dem CT-Board die Adresse.

FMC — Flexible Memory Controller — Bruecke zwischen internem AHB und externem Speicher.

NE — Not Enable / Chip Enable — active-low, definiert die Dauer eines Buszyklus.

NWE — Not Write Enable — active-low, kennzeichnet einen Schreibzugriff.

NOE — Not Output Enable — active-low, kennzeichnet einen Lesezugriff.

NBL — Not Byte Lane — gibt an, welche Bytes auf dem Datenbus gueltig sind.

SPI — Serial Peripheral Interface — synchrones, full-duplex serielles Protokoll (4 Leitungen).

MOSI — Master Out Slave In — Datenleitung Master zum Slave.

MISO — Master In Slave Out — Datenleitung Slave zum Master.

SCLK — Serial Clock — vom Master erzeugter SPI-Takt.

SS — Slave Select (NSS) — active-low Auswahlleitung je Slave.

NSS — Negated Slave Select — Hardware-Slave-Select-Pin der SPI-Peripherie.

CPOL — Clock Polarity — Ruhezustand des SPI-Takts (0 = LOW, 1 = HIGH).

CPHA — Clock Phase — Sampling an erster (0) oder zweiter (1) Taktflanke.

UART — Universal Asynchronous Receiver Transmitter — asynchrone serielle Schnittstelle (TX/RX).

I2C — Inter-Integrated Circuit — 2-Draht-Bus (SDA/SCL) mit 7-Bit-Adressierung, Open-Drain.

SDA — Serial Data — bidirektionale I2C-Datenleitung.

SCL — Serial Clock — vom Master erzeugter I2C-Takt.

ACK — Acknowledge — Empfaenger zieht SDA im 9. Takt auf LOW (Byte empfangen).

NACK — Not Acknowledge — SDA bleibt HIGH (Fertig oder Fehler).

TXE — Transmit buffer Empty — Sende-Datenregister ist bereit fuer das naechste Byte.

RXNE — Receive buffer Not Empty — ein empfangenes Byte steht bereit.

BSY — Busy — Uebertragung laeuft noch.

PWM — Pulse Width Modulation — Tastverhaeltnis-moduliertes Rechtecksignal.

PSC — Prescaler — teilt den Timer-Eingangstakt durch (PSC+1).

ARR — Auto-Reload Register — Maximalwert des Counters (Overflow bei ARR).

CCR — Capture/Compare Register — Vergleichs-/Einfangwert eines Timer-Kanals.

CNT — Counter — aktueller Zaehlerstand eines Timers.

ADC — Analog-to-Digital Converter — wandelt eine Spannung in eine Zahl 0..2^N-1.

DAC — Digital-to-Analog Converter — wandelt eine Zahl in eine Spannung.

LSB — Least Significant Bit — kleinste unterscheidbare Stufe: V_REF / 2^N.

FSR — Full Scale Range — groesster darstellbarer Bereich: V_REF - 1 LSB.

SAR — Successive Approximation Register — ADC per binaerer Suche, N Takte fuer N Bit.

EOC — End Of Conversion — Flag: ADC-Wandlung abgeschlossen.

OVR — Overrun — neues Ergebnis kam, altes wurde nicht gelesen.

DNL — Differential Non-Linearity — Abweichung einzelner Stufenbreiten von 1 LSB.

INL — Integral Non-Linearity — Abweichung der ganzen Kurve von der Idealgeraden.

SRAM — Static RAM — 6T-Flip-Flop-Zelle, schnell, kein Refresh, fluechtig.

DRAM — Dynamic RAM — 1T1C-Kondensatorzelle, Refresh noetig, guenstig, fluechtig.

SDRAM — Synchronous DRAM — getaktetes DRAM, schnell im Burst.

NOR — NOR Flash — wahlfreier Zugriff, XIP-faehig, fuer Code.

NAND — NAND Flash — nur Blockzugriff, hohe Dichte, fuer Massendaten (SSDs).

XIP — Execute In Place — Code direkt aus dem Flash ausfuehren (nur NOR).

CCM — Core Coupled Memory — 64 KB SRAM direkt am Core, kein DMA.

AMAT — Average Memory Access Time = Hit Time + Miss Rate * Miss Penalty.

LRU — Least Recently Used — Ersetzungsstrategie: aelteste Nutzung fliegt raus.

LFU — Least Frequently Used — Ersetzungsstrategie: seltenste Nutzung fliegt raus.

FIFO — First In First Out — Ersetzungsstrategie: aelteste Line fliegt raus.

FSM — Finite State Machine — endlicher Automat (Zustaende, Events, Transitionen).

UML — Unified Modeling Language — hier: Zustandsdiagramm-Notation.

ISR — Interrupt Service Routine — Funktion, die einen Interrupt bearbeitet.

IRQ — Interrupt Request — Interrupt-Anforderung (mit Nummer im NVIC).

NVIC — Nested Vectored Interrupt Controller — verwaltet/priorisiert Interrupts (Cortex-M).

MODER — GPIO Mode Register — Input/Output/Alternate/Analog je Pin (2 Bit).

OTYPER — GPIO Output Type Register — Push-Pull (0) oder Open-Drain (1), 1 Bit/Pin.

PUPDR — GPIO Pull-Up/Pull-Down Register — interne Widerstaende (2 Bit/Pin).

BSRR — Bit Set/Reset Register — atomares Setzen/Loeschen einzelner GPIO-Pins.

IDR — Input Data Register — liest den aktuellen Pin-Zustand.

ODR — Output Data Register — Ausgangszustand der Pins.
